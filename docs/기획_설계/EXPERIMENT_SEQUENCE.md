## 사용법

이 문서는 "무엇을, 어떤 순서로 할 것인가"만 다룬다. 배경·근거는 `STUDY_DESIGN.md` 해당 절 참조. 표시 기준:

- ✅ **확실/완료** — 근거가 탄탄하거나 이미 실기 완료
- ⚠️ **불확실** — 실기 확인 전이라 실패 가능성 있음(대안 있으면 같이 명시)

**중요**: 이 프로젝트에선 "확실해 보였는데 실기에서 다르게 나온" 사례가 여러 번(유튜브, 오브젝트 지우개, 노트 번역) 있었다. ⚠️ 항목은 다음 단계로 넘어가기 **전에** 반드시 먼저 확인할 것.

## Phase 1. 불확실성 우선 해소(실기 검증) — **데이터 수집 전 필수**

1. ⚠️ **[신규 최우선] llama.cpp 다중 인스턴스 동시 스케줄 검증** — `adb shell`로 2개 이상을 `D=HTP0`(또는 HTP0~4)로 동시 실행 시 실제로 같은 HTP에서 동시 스케줄되는지 `GGML_HEXAGON_VERBOSE=1` 로그의 큐 push/pop 인터리빙으로 확인. **조건 B 전체의 전제.** 직렬화 폴백 시 HTP 코어 분리 배정으로 조정.
2. ✅ **NPU 실제 점유 검증 — 완료(2026-08-10, S24U)** — 17/17 레이어 HTP0 배정, 실행 트레이스로 확인.
3. ⚠️ **모델·입출력 고정 사전 확인** — Qwen2.5-1.5B(4bit)이 구형 기기(S22/Flip4 등)에서 OOM 없이 로드되는지, `max_new_tokens` 고정.
4. ⚠️ **`dumpsys battery set level`이 실제 스로틀링을 유발하는지** — 조건 C(절전)에 필요.

## Phase 2. Tier 1 데이터 수집 — 5개 기기 + 데스크탑 단독 벤치마크 (= 조건 A)

✅ **확실**(프로토콜은 arXiv 2603.23640 그대로 채택)

1. 온도 22±2°C 환경 준비.
2. 기기별 순서: 임의(기기 간 교차오염 없음, 기기 내에서만 조건 사이 30분 냉각).
3. 각 기기 프로토콜: 10분 안정화 → 워밍업 폐기 → ΔT<2°C 확인 → 20회 반복(1초 간격) → 3세트.
4. NPU(`D=HTP0`) 메인, CPU(`D=CPU`)는 베이스라인 대조. 구형 기기(v69) HTP 미지원 시 CPU/CNN 경로로 대체.
5. S24U·S26U 데이터는 그대로 Tier 2 조건 A로 재사용.

## Phase 3. Tier 2 데이터 수집 — 멀티모델 동시실행(S24U/S26U만) (= 조건 B)

⚠️ **Phase 1-1(다중 인스턴스 동시 스케줄 검증)이 끝나야 시작 가능**

조건 A(Phase 2 재사용)와 동일 프로토콜·측정 항목으로, 같은 NPU에서 아래 조합을 동시 실행해 신규 측정:
- **B1** 이종(LLM + CNN) / **B2** 크기 다른 동종(대형 + 소형 LLM) / **B3** prefill×decode 겹침
- 동시 인스턴스 수 N을 자원 포화까지 스윕. 모델별 tok/s·합산 tok/s·간섭도(동시÷단독)·자원배분 대칭성 산출.
