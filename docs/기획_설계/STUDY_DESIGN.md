# 연구 설계 요약 (Study Design)

작성일: 2026-08-06 / **최종 갱신: 2026-08-11 (연구 방향 재설계 — Galaxy AI 경쟁실험 폐기 → 멀티모델 동시실행 + NPU 아키텍처 원인분석)** / 목적: 외부 검토(다른 AI 포함)를 위해 지금까지의 논의를 하나로 정리한 최종 요약본. **이 문서가 현재 확정된 계획의 단일 원천(single source)이며, 히스토리(왜 이렇게 바뀌었는지)만 `EXPERIMENT_PLAN.md`에 있다.**

## 1. 연구 배경

삼성 갤럭시 스마트폰(스냅드래곤 기반)에서 온디바이스 AI(LLM 등)를 반복 실행할 때,

1. 어떤 조건(NPU, 기기, 폼팩터)에서 추론 성능이 얼마나 유지·저하되는지 (CPU는 베이스라인 대조용, **GPU는 측정 대상에서 제외 — 2026-08-11**)
2. **여러 온디바이스 AI 모델이 같은 NPU(Hexagon HTP)를 동시에 점유할 때 처리량·지연·전력이 어떻게 저하·간섭되는지**, 그리고 그 간섭 패턴이 **S24U(HTP v75)와 S26U(HTP v81)의 아키텍처 세대차로 어떻게 설명되는지**
3. 삼성이 광고하는 세대 간 성능 개선("NPU 39% 향상, 멀티태스킹 문제없음")이 단독뿐 아니라 **동시실행·절전 같은 실사용 제약 조건에서도** 유지되는지

를 실측한다.

> **⚠️ 2026-08-11 방향 재설계**: 기존 2번은 "삼성 자사 AI(Galaxy AI)와의 경합 및 공정성(RQ7)"이었으나, Galaxy AI가 블랙박스 앱이라 추론 성능을 직접 측정할 수 없는 근본 한계(카메라 프레임 분석 우회 의존)로 **폐기**했다. 대신 경합 상대를 우리가 통제 가능한 우리 측 멀티모델로 바꿔 **전 워크로드를 화이트박스(llama.cpp)로 직접 계측**하고, 세대별 NPU 아키텍처 조사(§5-A)로 원인을 설명한다.

## 2. 선행연구와의 관계

가장 가까운 선행연구는 **"LLM Inference at the Edge: Mobile, NPU, and GPU Performance Efficiency Trade-offs Under Sustained Load"**(arXiv 2603.23640, 2026)로, 4개 플랫폼(노트북 GPU / RPi5+Hailo-10H / iPhone 16 Pro / Galaxy S24 Ultra)에서 동일한 프로토콜(지속부하 20회 반복)로 플랫폼별 성능 열화 패턴을 비교함.

우리 실험은 이 논문의 프로토콜(10분 열안정화 → 워밍업 폐기 → 20회 반복 → 3세트)을 그대로 채택하되, 다음을 확장한다:

- 삼성 기기를 1대가 아니라 **5대 + 데스크탑**(추후 엣지가속기)으로 확장
- 선행연구가 GPU만 본 것과 달리 **NPU 추론 성능**에 집중(CPU는 베이스라인 대조용, GPU는 측정 대상에서 제외 — 우리 연구의 관심은 NPU 성능과 추론 성능)
- **동일 NPU 상 여러 독립 모델의 동시실행 간섭을 정량 특성화하고, 이를 세대별 Hexagon 아키텍처(v75 vs v81)로 인과 설명**하는 축을 추가(핵심 기여). Puzzle(arXiv 2508.17764)이 "한 모델을 쪼개 배치"하는 것과 달리 우리는 "여러 독립 모델의 동일 NPU 경합 + 아키텍처 원인분석"으로 문제 설정이 다름.

## 3. 실험 구조 — 2단계(Tier)

### Tier 1. 전체 플랫폼 비교 (넓게, **선택 확장** — 2026-08-12 지도교수 승인으로 범위 축소)

> **⚠️ 2026-08-12 확정**: 지도교수가 **"S24U·S26U 두 기기만으로도 충분하다"**고 승인함에 따라, 이 프로젝트의 **필수 확정 범위는 Tier 2(S24U vs S26U)**이고, 아래 6기기 전체 비교(Tier 1)는 **시간이 남으면 진행하는 선택 확장 과제**로 격하한다. 이유는 두 가지: (1) 지도교수 승인으로 범위를 좁혀도 무방해짐, (2) 구형 기기 3종(S22/Fold4/Flip4)이 llama.cpp Hexagon NPU 백엔드(HTP v69 미포함, 6장·아래 참고)를 지원하지 않아 이 3대를 포함하면 "기기·폼팩터 차이" 비교가 아니라 "NPU vs CPU 백엔드 차이" 비교로 오염되는 방법론적 문제가 있었음(다른 AI 도구 비평, 2026-08-12 — `EXPERIMENT_PLAN.md` 26장 참고).

**목적**: 플랫폼마다 지속부하 시 성능 저하 "패턴의 종류" 자체가 다른지 확인(선행논문의 핵심 통찰 — 안드로이드는 완만한 하락, iOS는 계단식 급락 — 을 삼성 내부 다양성 + 새 플랫폼으로 확장 재현).

| 플랫폼 | 유형 | 확보 상태 | 범위 |
|---|---|---|---|
| Galaxy S24 Ultra | 바형, 2024세대(Snapdragon 8 Gen3) | 보유 | **필수(Tier 2 겸용)** |
| Galaxy S26 Ultra | 바형, 2026세대 최신(Snapdragon 8 Elite Gen5) | 보유 | **필수(Tier 2 겸용)** |
| Galaxy S22 | 바형, 2022세대(Snapdragon 8 Gen1) | 보유 | 선택 확장 |
| Galaxy Z Fold4 | 폴더블, 2022세대(Snapdragon 8+ Gen1) | 보유 | 선택 확장 |
| Galaxy Z Flip4 | 클램쉘, 2022세대(Snapdragon 8+ Gen1) | 보유 | 선택 확장 |
| 데스크탑(RTX 4080) | 고정형, 전력·냉각 무제약 | 보유 | 선택 확장 |
| Jetson Orin Nano | 저전력 전용 엣지 가속기 | 미보유 | 선택 확장 |

**방법**: 동일 모델(LLM 또는 CNN)을 각 플랫폼에서 단독으로 지속부하 프로토콜(아래 4장) 실행 후 회차별 성능 곡선 비교.

**선택 확장을 실제로 진행할 경우의 필수 조건**: S22/Fold4/Flip4를 넣으려면 반드시 **CPU 트랙(6기기 전부 동일하게 `D=CPU`)**과 **NPU 트랙(S24U·S26U만 `D=HTP0`)**을 분리된 비교로 취급한다 — 한 표에 "S22=CPU, S24U=NPU"처럼 백엔드가 섞인 채로 "기기 차이"라고 결론 내리지 않는다(6장 리스크 표 참고).

### Tier 2. 삼성 세대 비교 — 핵심 기여 (좁고 깊게)

**목적**: 여러 모델이 같은 NPU를 동시 점유할 때의 간섭을 정량화하고, 삼성이 광고하는 세대 간 성능 개선이 **단독뿐 아니라 동시실행·절전 제약에서도 유지되는지** + 그 차이가 **아키텍처 세대차로 설명되는지** 확인.

**대상**: Galaxy S24 Ultra(HTP v75) vs Galaxy S26 Ultra(HTP v81) — 두 기기의 Hexagon 세대차가 핵심 관측 대상.

| 조건 | 내용 | Tier 1 데이터 재사용 |
|---|---|---|
| A. 단독(baseline) | 모델 1개 단독 실행 | O(Tier 1과 동일 데이터) |
| B. 멀티모델 동시실행 | 같은 NPU에서 2개 이상 모델 동시 실행(아래 B1/B2/B3) | X(신규 측정, **핵심**) |
| C. 제한된 상황 | 절전모드/성능제한모드 | X(신규 측정, 대표 기기 위주) |

세 조건을 S24U·S26U 둘 다에서 비교해 **"S26U의 성능 우위가 동시실행·절전에서도 유지되는가, 줄어드는가"** + **"V81의 동시성 최적화가 실제로 간섭을 줄이는가"**를 본다 — 이 질문이 논문의 핵심 기여.

#### Tier 2 조건 B — 멀티모델 동시실행 워크로드 설계(2026-08-11 재설계)

동시성은 **2-way부터 시작**해 자원 포화가 관찰될 때까지 동시 인스턴스 수 N을 스윕. 아래 세 조합을 모두 측정한다.

- **B1. 이종 조합(LLM + CNN)**: 메모리 대역폭 병목형(LLM decode) + 연산집약형(CNN)이 서로 다른 자원을 다투는 간섭. LLM=Qwen2.5-1.5B(4bit), CNN=ResNet/YOLOv8(Qualcomm AI Hub, HTP v69~v81 지원).
- **B2. 크기 다른 동종(대형 LLM + 소형 LLM)**: 같은 성격 워크로드의 스케줄링·우선순위·starvation 관측. VTCM 포화가 크기차로 드러남.
- **B3. 단계 겹침(prefill × decode)**: 한 모델 prefill(연산집약) × 다른 모델 decode(대역폭집약)를 겹쳐 NPU 내부 연산·메모리 경로 배분 관측.
- **B4. 앱 상태(FG/BG) 조합 — GenieX 병행 검증(2026-08-12 추가, ⏸️ 2026-08-12 보류 결정 — 후순위)**: B1~B3은 두 인스턴스를 전부 `adb shell` CLI로 강제 foreground 처리해서 돌리는데, 이건 실제 안드로이드 사용자가 "한 앱을 쓰는 동안 다른 앱이 백그라운드에서 도는" 실사용 시나리오와 다르다. 이를 실측으로 검증하기 위해 **GenieX 앱(실제 GUI 앱, 진짜 foreground/background 생명주기 있음) 1개 + llama.cpp CLI 1개**를 동시 실행해 세 조합을 비교한다(설계는 유지, 착수는 보류):
  - **FG×FG**: GenieX 화면에 보이는 상태(스플릿스크린 등) + llama.cpp CLI를 기존처럼 foreground cgroup으로 강제(§3 핵심설계원칙 방식) — B1~B3의 기존 측정과 대응
  - **FG×BG**: GenieX는 화면에 보이는 상태, llama.cpp CLI는 별도 강제 없이 adb shell 기본 우선순위 그대로
  - **BG×BG**: GenieX를 최소화(백그라운드)한 상태 + llama.cpp CLI도 기본 우선순위 — 가장 현실적인 "두 AI가 동시에 백그라운드에서 도는" 시나리오
  - **목적**: §3 핵심설계원칙에서 제기한 "CLI 페널티가 조건마다 다를 수 있다"는 우려를, 가정이 아니라 **진짜 앱 상태 차이로 직접 실측**해서 검증. FG×FG(현재 방법론)와 BG×BG 간 간섭도 차이가 크면, 지금까지의 B1~B3 결과가 "최선의 경우(foreground 강제)"만 잡아낸 것이고 실사용 환경에서는 간섭이 더 클 수 있다는 뜻.
  - **진행 상태 — 보류(2026-08-12 확정)**: S26U는 GenieX가 이미 잘 동작하는 걸 확인했으니(2026-08-05경 설치·실기 추론 성공), **당장은 S24U 설치를 포함해 GenieX/B4 관련 작업 전체를 미루기로 결정**. 이유를 특별히 밝히진 않았지만, S26U 하나로도 충분히 검증됐다고 판단한 것으로 보임 — 필요해지면 재개.
  - **재개 시 필요한 것(참고용, 지금 당장 할 일 아님)**: S24U에 GenieX 설치(B4는 S24U·S26U 둘 다 필요), GenieX에 로드된 모델을 연구용 본 모델(Qwen2.5-1.5B 4bit)로 통일(현재는 테스트용 소형 모델, 모델명 미확인).
  - **순서**: B1~B3(핵심 데이터, Phase 3) 완료 후에도 **바로 이어지지 않고 보류** — 재개 여부는 추후 판단.

**동시 실행 방법(B1~B3)**: llama.cpp 인스턴스를 `adb shell`로 2개 이상 동시 실행, 각각 `D=HTP0`(또는 HTP0~4 코어 분리) 지정. QAIRT상 다중 그래프 동시 실행은 전 기기 가능, **"Concurrent Resource Sharing" 최적화는 V81(S26U) 한정** — 이 차이가 세대 비교의 핵심.

#### 핵심 설계 원칙 — OS 백그라운드 스로틀링 통제

- **전 인스턴스 foreground 유지**: 동시 실행하는 llama.cpp 프로세스가 OS cgroups 백그라운드 제약을 받지 않도록 관리한다. `adb shell` CLI 실행은 GUI 앱보다 커널 우선순위가 낮으므로(11-6), 모든 인스턴스를 동일 방식으로 실행한다.
  - **⚠️ "동일 방식으로 실행하면 대칭성이 자동 보장된다"고 가정하지 않는다(2026-08-12, 다른 AI 도구 비평 반영)**: 절전모드(조건 C)·동시실행(조건 B)에서는 안드로이드 스케줄러(PowerHAL 등)가 포그라운드 GUI 앱과 백그라운드/비대화형 CLI(adb shell) 프로세스에 서로 다른 DVFS·코어 배정 정책을 적용할 수 있다. 즉 CLI 페널티 자체가 조건 A/B/C마다 다를 수 있어, "전 조건에 동일 페널티니 상대비교는 공정하다"는 가정이 조건 C·B에서는 깨질 위험이 있다. **Phase 1에서 조건 A/B/C 각각에 대해 `adb shell dumpsys cpuinfo`와 `cat /proc/<PID>/cgroup`으로 llama.cpp 프로세스가 실제로 P-코어에 남는지 E-코어로 강제 이주당하는지 실측·기록**한다 — 대칭성을 가정이 아니라 수치로 확인.
- **배터리 설정 '제한 없음'**: OS 레벨 배터리 최적화 스케줄러 개입을 차단해, 남는 격차를 NPU/스케줄러 자체 효과로 좁혀 해석한다.
- **아키텍처 원인분석 병행**: 조건 B의 간섭 결과는 §5-A의 NPU 아키텍처 조사(v75 vs v81 스펙 + 마이크로벤치)로 인과 설명한다.

## 4. 실험 순서

> **⚠️ 용어 구분 — 이 문서에는 서로 다른 두 개의 축이 나온다. 혼동하지 말 것.**
>
> | 축 | 의미 | 값 |
> |---|---|---|
> | **Phase** | 실험을 **언제, 어떤 순서로** 하는가(실행 순서) | Phase 0(준비) → 1(검증) → 2(Tier1 측정) → 3(Tier2 측정) → 4(분석) |
> | **조건 A/B/C** | 같은 벤치마크를 **어떤 제약 상태에서** 도는가(3장 Tier 2 전용) | A(제약 없음) / B(Galaxy AI 동시실행) / C(절전모드) |
>
> 즉 아래 **Phase 2에서 조건 A(제약 없음) 데이터를 모으고**, **Phase 3에서 같은 벤치마크·같은 측정 항목을 조건 B·C(제한된 상황)로 다시 돌려서** 조건 A와 직접 비교한다. 조건 A/B/C는 셋 다 동일한 프로토콜·동일한 측정 항목을 쓰고, 오직 "제약이 있는가/없는가"만 다르다 — 그래야 차이가 나면 그게 온전히 그 제약 때문이라고 말할 수 있다.

| 트랙 | 출처 | 용도 | 논문 직접비교 |
|---|---|---|---|

**ShareGPT 샘플링 방법**: 각 대화의 첫 사용자 turn을 프롬프트로 추출 → 토큰 길이 기준 짧음(<100)/중간(100~500)/긴(500+) 3버킷 × 3개, 총 9개를 고정 시드로 무작위 샘플링(재현성 확보, 시간 부족 시 버킷당 1개로 축소 가능). `max_new_tokens`는 버킷별로 고정. 실험 투입 전 9개 프롬프트를 육안으로 확인해 개인정보·부적절 콘텐츠가 없는지 점검(원본이 실사용자 채팅 스크랩이므로).

**⚠️ 분석 시 TTFT(prefill)와 decode를 반드시 분리 파싱한다(2026-08-12, 다른 AI 도구 비평 반영)**: 논문 비교 트랙은 프롬프트 길이가 고정이라 tok/s 하나로도 비교가 성립하지만, ShareGPT 트랙은 버킷마다 입력 길이가 다르다. Prefill(연산집약)은 입력 길이에 비선형적으로 늘어나고 decode(대역폭집약)는 출력 토큰당 거의 선형이라, 두 값을 뭉뚱그린 aggregate tok/s만 보면 "짧은 프롬프트가 빠르다"는 착시가 생길 수 있다. §5 측정표의 `ttft_ms`·`prefill_time_ms`·`decode_time_ms`(이미 CSV 스키마에 있음)를 버킷별로 반드시 나눠서 분석하고, 버킷 간 비교는 절대 tok/s가 아니라 **prefill 지연(TTFT)과 decode의 토큰당 시간(time-per-output-token)을 각각 따로** 비교한다.

2. Tier 1: 플랫폼 간 곡선 **형태**(완만/급락/거의 평평) 비교.
3. Tier 2: 조건 A/B/C별 S24U-S26U 격차 비교 — 격차가 좁혀지면 "동시실행·제약 상황에서 삼성의 세대 우위가 줄어든다"는 결론.
4. Tier 2-B: 동시실행 조합(B1/B2/B3)별 간섭도를 S24U·S26U 나란히 비교하고, 두 모델 간 자원배분 대칭성 분석. 세대차가 나면 아래 §5-A 아키텍처 조사로 원인 설명.
5. **B1/B2 간섭 원인을 "NPU 내부 vs 외부 DRAM"으로 분리한다(2026-08-12, 다른 AI 도구 비평 반영)**: decode는 이미 memory-bandwidth-bound로 확인됐으므로(Phase 1), B1/B2에서 성능이 떨어졌다고 곧바로 "NPU 코어/VTCM 경합"으로 결론 내리지 않는다 — 두 모델이 요구하는 LPDDR 대역폭의 합이 물리적 상한을 넘어 **DRAM 버스에서** 병목이 생겼을 수도 있고, 이 경우 v81의 아키텍처 개선(HMX/HVX, Concurrent Resource Sharing)으로는 해소되지 않는다. **B3(prefill×decode 겹침)를 이 둘을 가르는 통제실험으로 명시적으로 쓴다**: prefill(연산집약)이 눌리면 NPU 내부(HMX/VTCM) 경합, decode(대역폭집약)가 눌리면 DRAM 버스 경합으로 해석.

## 5-A. NPU 아키텍처 조사 (원인분석의 근거)

**대상**: Hexagon **HTP v75**(S24U / SM8650 / Snapdragon 8 Gen3) vs **HTP v81**(S26U / SM8850 / 최신). 조건 B의 간섭 패턴(§5)의 "왜"를 이 조사로 설명한다.

> **출처 표기(2026-08-12)**: 아래 A-1 항목 중 SLC 공유 정책·Battery Level Governor/PowerHAL·열 단계별 하강(step throttling)·방열 구조 비교·드라이버(QNN/Samsung ENN) 비교·CPU 스레드 코어 마이그레이션과, A-3 sysfs 폴링 기법은 다른 AI 도구(ChatGPT)가 작성한 초안을 병합한 것이며 이 프로젝트에서 원문 대조 검증을 아직 거치지 않았다. 특히 정확한 sysfs 경로명(`*npu*`, `*cdsp*` 등 와일드카드)·"Samsung ENN" 드라이버 존재 여부·배터리 15~20% 임계값 같은 구체 수치는 **실기에서 직접 확인 전까지 미확정**으로 취급한다(§6에 리스크로 반영).

**A-1. 문헌·공식자료 조사 (조사 항목)**
- **연산 유닛**: HMX(행렬/텐서 엔진)·HVX(벡터) 폭·개수, 세대별 tensor 처리량, INT8/FP16/INT4 등 데이터 타입별 가속 방식과 전력 대 성능비(Perf/Watt)
- **온칩 메모리**: VTCM(On-Chip SRAM) 용량·대역폭 — 멀티모델 시 포화점의 직접 원인(가중치·Activation이 SRAM 용량을 초과하면 DRAM 트래픽 급증 → Latency 폭증)
- **메모리 대역폭**: LPDDR 세대·Bus Width·시스템 대역폭 — decode 병목의 상한, 2개 이상 모델 동시추론 시 DRAM 대역폭 경합(조건 B 직결)
- **SLC(System Level Cache) 공유 정책**: CPU/GPU/NPU가 SLC를 공유하는 방식, 절전 모드 전환 시 SLC 클럭/파워 도메인 제한 여부
- **클럭·전력 도메인(DVFS)**: NPU DVFS 테이블·Clock Capping — 절전 모드(조건 C) 진입 시 NPU·DRAM 최대 동작 주파수 상한 제어값. **Battery Level Governor**: 배터리 잔량(예: 15~20% 이하)에 따른 PowerHAL의 NPU 터보클럭 진입 제한 정책 — 조건 C 설계와 직결되는 항목이라 우선순위 높음
- **열 관리(Thermal Throttling)**: 다중 모델 연속 추론 시 SoC 온도 상승에 따른 NPU·DRAM 주파수의 단계별 하강(step throttling) 임계값, 기기별 방열 구조(Vapor Chamber 등) 차이가 피크 대비 지속 성능 유지율에 미치는 영향 — Tier 1의 기기 간(S22~S26U) 비교 해석에 직결
- **동시성 지원**: 다중 컨텍스트/그래프 스케줄링, **V81 "Concurrent Resource Sharing"**의 실제 정의·적용 범위
- **NPU 드라이버 및 스케줄링**: Qualcomm QNN(및 삼성 자체 NPU 런타임이 별도로 개입하는지)의 다중 모델 Time-slicing 컨텍스트 스위칭 오버헤드, 전/후처리 CPU 스레드가 절전 모드에서 P-코어→E-코어로 마이그레이션되는지 여부
- 출처: Qualcomm 공식 문서/개발자 블로그, Hexagon SDK 문서, `RELATED_PAPERS.md`(칩세대 일치 논문)

**A-2. 마이크로벤치 (실측으로 문헌 뒷받침)**
- **메모리 대역폭 roofline**: 연산강도 대비 처리량 → decode 병목이 대역폭임을 v75/v81 각각에서 정량화
- **VTCM 포화점**: 모델/배치 크기를 키우며 성능이 꺾이는 지점 → 조건 B2(크기차 조합) 해석 근거
- **컨텍스트 스위칭 비용**: 동시 인스턴스 수 N을 늘리며 HTP 큐 타이밍 증가 측정
- **지속 클럭**: 열안정화 후 유지 클럭 세대 비교
- 도구: `llama-bench`·기존 verbose 로그 우선 활용, 커스텀 커널은 최소화. 실시간 클럭·온도 관측은 아래 A-3 참고

**A-3. 블랙박스 역분석 — Sysfs 실시간 폴링(2026-08-12 추가, 실기 검증 전)**

Snapdragon Profiler(§5 표, S24U·S26U만 공식 지원)가 커버하지 못하는 기기(S22/Fold4/Flip4)나 세부 커널 노드를 보완하기 위해, 루팅 없이 `adb shell`로 커널 sysfs 노드를 주기적으로 폴링하는 방법을 병행 검토한다.

```bash
# NPU / CDSP 동작 주파수 실시간 모니터링
adb shell "cat /sys/class/devfreq/*npu*/cur_freq"
adb shell "cat /sys/class/devfreq/*cdsp*/cur_freq"

# SoC thermal zone 온도 확인
adb shell "cat /sys/class/thermal/thermal_zone*/temp"
```

> **실기 검증 필요**: 위 경로의 와일드카드(`*npu*`, `*cdsp*`)가 실제 우리 기기(S24U/S26U)에서 어떤 이름으로 노출되는지, 권한(퍼미션) 문제로 값이 안 읽히는지 Phase 1에서 `adb shell find /sys/class/devfreq -maxdepth 1`, `adb shell find /sys/class/thermal -maxdepth 1`로 먼저 확인한다.
>
> **⚠️ sysfs는 보조 수단으로 격하, Snapdragon Profiler를 메인으로(2026-08-12, 다른 AI 도구 비평 반영)**: 최신 안드로이드(14/15/16)·SoC(SM8650/SM8850)는 보안·파워도메인 개편으로 NPU/CDSP 동작 주파수를 비루팅 `adb shell` 권한에 아예 노출하지 않거나(권한 거부), `/sys/kernel/debug/...` 같은 루팅 필요 경로로 옮겨뒀을 가능성이 높다. 그러므로 이 A-3 sysfs 폴링은 **Snapdragon Profiler(§5 표, S24U·S26U 공식 지원 확인됨)가 못 잡는 세부 항목을 보완하는 2차 수단으로만 쓰고**, Phase 1에서 위 `find` 명령으로 값이 실제로 읽히는지부터 확인한 뒤 안 읽히면 즉시 포기하고 Snapdragon Profiler 실측으로 전환한다 — sysfs 경로를 억지로 고집하지 않는다.

> **주의(프로젝트 원칙)**: 위 스펙 수치는 조사 대상이지 확정값이 아니다. "문서상 값 ≠ 실기값"일 수 있으므로 문헌 스펙은 반드시 A-2 마이크로벤치로 교차확인하고, 불일치 시 실측을 우선한다.
