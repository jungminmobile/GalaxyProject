## 1. 난이도 3단계(Tier) 구조 — 왜 이렇게 나눴는가

`SNAPDRAGON_FEASIBILITY.md` 10장에서 확인했듯, GenieX의 공식 Android Kotlin API(`ModelConfig`)는 `nCtx`, `nThreads`, `nBatch`, `compute_unit` 등은 노출하지만 **HTP Performance Profile이나 Graph Priority는 노출하지 않음**(raw QNN/QAIRT C++ 레벨 기능). 그래서 "얼마나 깊이 들어갈 것인가"에 따라 3단계로 나눔 — 시간이 부족하면 Tier 1만으로도 질문 1~3에 답이 되고, 여유가 있으면 Tier 3까지 확장.

| Tier | 난이도 | 필요 기술 | 답할 수 있는 질문 |
|---|---|---|---|
| **1** | 낮음 | Kotlin(GenieX SDK)만 | 질문 1, 2, 3 |
| **2** | 중간 | Tier1 + Android 표준 API(ADPF) + Snapdragon Profiler(데스크톱, USB 연결) | 질문 3(정밀 계측), NPU/GPU 실시간 사용률·클럭 관측 |
| **3** | 높음 | Tier1~2 + Android NDK/C++로 raw QNN(QAIRT) SDK 직접 호출 | 질문 4 |

### 2-4. 배경 부하(백그라운드 앱) — 실사용 환경 재현 (2026-08-04 추가)

연구 질문 6번 대응. 기존 6장 매트릭스(A~E)에 곱해지는 **추가 축**으로 취급 — 즉 "조건 A를 BL0/BL1/BL2에서 각각 실행"하는 식으로 확장. BL3(멀티태스킹)은 정식 매트릭스에 넣지 않고 **선택적 추가 실험**으로만 취급(시간 여유 있을 때).

| 레벨 | 상태 | 설정 방법 | 비고 |
|---|---|---|---|
| **BL0** (베이스라인) | 백그라운드 앱 없음, 화면 꺼짐 | 기존 5장 프로토콜 그대로 | 지금까지 계획하던 기본 조건 |
| **BL1** (가벼운 부하) | 음악/오디오 스트리밍 앱이 오디오만 재생 중 | 유튜브 뮤직 등 실행 후 재생, 화면은 꺼도 무방(오디오 세션은 유지됨) | CPU/네트워크에 가벼운 상시 부하 |
| **BL2** (무거운 부하) | 유튜브 동영상 재생 중 | **스플릿 스크린(화면 분할)으로 GenieX 앱과 나란히 띄워서 실행** — 완전히 최소화(백그라운드)만 시키면 안드로이드가 화면에 안 보이는 동영상 디코딩을 절전 목적으로 줄이거나 멈출 수 있어 재현성이 떨어짐. 스플릿 스크린이면 화면에 계속 보이므로 디코딩 부하가 확실히 유지됨 | 화면이 켜져 있어야 하므로 5장 프로토콜의 "화면 꺼짐" 전제와 충돌 — BL2에서는 화면 on 상태를 별도로 기록하고 배터리 측정치 해석 시 이 점을 감안할 것 |
| **BL3** (멀티태스킹, 선택) | 최근 앱 목록에 카메라 프리뷰·브라우저·SNS 등 여러 개를 백그라운드로 띄워둔 상태 | 6-4 참고, 시간 여유 시 추가 실험으로 진행 | 정식 매트릭스 미포함 |

> **(2026-08-05 실기 확인) BL2(유튜브)가 실제로 GPU 부하를 주는지는 아님 — 실측으로 반박됨.** 4K 유튜브 재생 중 Snapdragon Profiler로 GPU % Utilization을 관찰한 결과 1% 미만으로, LLM 추론이 없는 유휴 상태와 다를 바 없었음. 원인: 동영상 디코딩은 Adreno GPU(3D 그래픽 엔진)가 아니라 **전용 비디오 코덱 하드웨어(Venus 등)**가 처리하며, GPU는 디코딩된 프레임을 화면에 얹는 가벼운 컴포지팅만 수행함. 즉 BL1(음악)/BL2(유튜브)는 "GPU/NPU 연산 자원을 LLM 추론과 놓고 경쟁시킨다"는 원래 의도된 부하 메커니즘으로는 작동하지 않고, 대신 **메모리 대역폭 공유·열 예산 공유·배터리 소모**를 통한 간접적 영향만 줄 가능성이 높음. 만약 "GPU/NPU 연산 자원 경쟁"을 정말로 재현하고 싶다면 유튜브 대신 **3D 게임이나 GPU 벤치마크 앱**(실제로 Adreno GPU를 점유하는 앱)으로 BL2를 재정의해야 함 — 다만 이는 계획 변경이 필요한 사항이라 우선 이 한계로 기록만 해두고, 정식 변경은 추후 판단.

## 4. 모델·데이터 선정

- **주 모델**: Qwen 계열 소형 LLM, 4bit 양자화(Q4_0) — GGUF는 `unsloth/Qwen3-0.6B-GGUF` 등, NPU 전용 비교용은 `ai-hub-models/Qwen3-4B-Instruct-2507`(pull 시 `chipset="SM8850"` 필수 지정).
- **프롬프트(논문 비교용, 고정)**: 고정된 하나의 긴 서술형 프롬프트 — arXiv 2603.23640v2 §3.2에 원문 그대로 실려 있는 258토큰(Qwen2.5 BPE 기준) "consciousness를 여러 관점에서 설명하는 에세이" 프롬프트를 그대로 재사용(2026-08-12 원문 대조로 인용 검증 완료 — https://arxiv.org/html/2603.23640v2 §3.2). 그러면 그 논문의 실측치와 직접 비교도 가능.
- **프롬프트(현실 입력 분포용, 신규)**: ShareGPT 데이터셋 기반 다양한 길이·내용의 프롬프트를 추가 트랙으로 병행 측정(2026-08-12 확정, 상세는 §25).
- **디코딩 설정**: greedy(temperature=0, top-k=1)로 고정해 출력 길이를 결정적으로 만듦(반복 간 노이즈 제거).
- **비교용 대안 모델**: 원래 프로젝트가 CV(YOLOv8)였던 점을 고려해, 여유가 있으면 Qualcomm AI Hub의 YOLOv8-Detection도 QNN(HTP)으로 실행해 "LLM은 GPU/NPU 어디가 유리한지"와 "CV 모델은 NPU가 확실히 유리한지"를 대조하는 것도 가능(9장에서 이미 YOLOv8은 HTP v69/v81 전부 공식 지원 확인됨).

## 5. 실험 프로토콜 (arXiv 2603.23640 방법론을 그대로 채택 — 이미 S24 Ultra에서 검증된 절차)

1. 기기를 22±2°C 상온에서 **10분간 열 안정화**.
2. 모델을 메모리에 로드하고 **워밍업 1회 실행 후 결과 폐기**.
3. 60초간 온도 변화가 2°C 미만(ΔT<2°C)인지 확인 후 본 실험 시작.
4. 화면은 꺼진 상태 유지(배터리 측정 정확도를 위해, 8-4 논문과 동일).
5. 하나의 조건(독립변인 조합)마다 **20회 반복, 반복 간 1초 대기**.
6. 매 반복마다 CSV 한 줄 기록: `timestamp, condition_id, decode_tokens, decode_time_ms, prefill_time_ms, throughput_tok_s, ttft_ms, battery_temp_c, battery_current_ma, battery_voltage_mv, thermal_status, (Tier2)npu_util_pct, (Tier2)gpu_freq_mhz`.
7. 조건이 바뀔 때마다 **기기를 30분 이상 식히거나 재부팅**해서 이전 조건의 잔열이 다음 조건에 영향을 주지 않게 함.
8. 각 조건은 **3세트 반복**(재현성 확인 — Hailo 프로젝트에서 쓰던 관례와 동일).

### 6-1. 최소 실행 버전(Tier 1만, 우선 이것부터)

| 조건 ID | runtime | compute_unit | 디스패치 | 비고 |
|---|---|---|---|---|
| A | llama_cpp | npu | hybrid(기본) | 가장 빠를 것으로 예상되는 기본값 |
| B | llama_cpp | npu | pinned HTP0 | 결정적이지만 느릴 것으로 예상 |
| C | llama_cpp | gpu | — | Adreno GPU 경로 |
| D | llama_cpp | cpu | — | 순수 CPU 베이스라인 |
| E | qairt | npu(전용) | — | AI Hub 사전컴파일 NPU 경로(고정 context) |

→ 5조건 × 20회 × 3세트 = **300회 실행**. 조건당 예상 소요시간을 고려해 하루 안에 끝내기 어려우면 조건 수를 A/B/D 3개로 줄여도 질문 1·2는 답변 가능.

### 6-2. 확장 버전(Tier 3까지, S26 Ultra 심화)

6-1의 조건 A(가장 성능 좋은 조합) 위에 **HTP Performance Profile 4수준**(burst/balanced/low_power/sustained_high_performance) × **Graph Priority 2~3수준**(낮음/기본/높음)을 추가로 곱해 조건을 확장. 이건 raw QNN NDK 코드가 필요하므로 시간 여유에 따라 선택.

### 6-3. 기기 간 비교(선택, S22/Fold4/Flip4)

6-1의 조건 A/D(가장 단순한 hybrid, cpu)만 골라 세 기기에서 동일하게 실행 — Snapdragon Profiler/NPU 클럭 계측은 빼고 Tier 1 측정치(tok/s, 온도, 배터리)만으로 "동일 세대 칩, 폼팩터별 스로틀링 차이"를 비교.

### 6-4. 배경 부하(BL0~BL3) 결합 매트릭스 (2026-08-04 추가)

2-4의 배경 부하 레벨을 6-1의 조건과 곱해서 확장. 시간이 부족하면 조건 수를 줄여서(예: A만) 대표 조건 하나로 BL0~BL2 세 단계만 비교해도 연구 질문 6번에 답변 가능.

| | BL0(베이스라인) | BL1(음악) | BL2(유튜브 스플릿) |
|---|---|---|---|
| 조건 A (hybrid) | 기존 계획대로 | 추가 | 추가 |
| 조건 C (gpu) | 기존 계획대로 | 추가 | 추가 |
| 조건 D (cpu) | 기존 계획대로 | 추가 | 추가 |

→ 최소 버전: **조건 A만 BL0/BL1/BL2 세 단계** = 3조건 × 20회 × 3세트 = 180회 실행 추가. 여유 있으면 C, D까지 확장.

**BL3(멀티태스킹)은 이 매트릭스에 포함하지 않고 정식 조건 완료 후 시간 남으면 진행하는 추가 실험으로 취급** — 대표 조건 하나(A 등)만 골라 BL3에서 몇 회 돌려보고 정성적으로 비교하는 정도로 충분.

### 10-A-1. llama.cpp Hexagon(HTP) 백엔드를 CLI로 직접 실행 — **실현 가능성 확인됨, 유력한 2차 측정 경로**

**배경**: "GenieX 앱 말고 PC 터미널에서 폰 모델을 돌릴 수 없나?"라는 질문에서 출발. 처음엔 "NPU는 CLI로 못 쓴다"고 판단했으나 **공식 llama.cpp 문서 확인 결과 이는 오답이었고, 정정함.**

공식 저장소에 Hexagon NPU 백엔드가 이미 병합되어 있음(`ggml-org/llama.cpp` → `docs/backend/hexagon/README.md`, PR #16547):

- **세 백엔드 모두 CLI에서 선택 가능**: 공식 문서 원문 — "llama.cpp supports three backends on Snapdragon-based devices: CPU, Adreno GPU (GPUOpenCL), and Hexagon NPU (HTP0-4). You can select which backend to run the model on using the `D=` variable". 즉 `D=HTP0` / `D=GPUOpenCL` / `D=CPU`로 지금 GenieX 앱에서 버튼으로 하던 조건 전환을 명령어로 대체 가능.

- **측정 자동화 이점이 큼**: `llama-bench`가 prefill(pp)/decode(tg) 처리량을 표준편차까지 붙여 표로 출력함. 예시: `| llama 1B Q4_0 | HTP | pp128 | 169.42 ± 1.75 |`, `| ... | tg64 | 51.54 ± 1.13 |`. 현재 GenieX 앱에서 수동으로 하는 20회 반복 측정을 스크립트로 자동화할 수 있음.

- 빌드에 Docker + 전용 툴체인 이미지(`ghcr.io/snapdragon-toolchain/arm64-android`, Android NDK·Hexagon SDK·OpenCL SDK 포함) 필요 — 설치·빌드 시간 소요.

### 10-A-2. prefill/decode 단계별로 다른 compute unit 할당 — **아이디어는 유효하나 GenieX로는 실행 불가**

**배경**: "전처리·prefill·decode를 모두 같은 곳에서 처리 vs 서로 다른 곳에서 처리"라는 아이디어.

- 이 발상 자체는 클라우드 LLM 서빙에서 **"prefill-decode disaggregation"**이라는 이름으로 이미 활발히 연구·상용화된 실제 방향임(vLLM, SGLang, TensorRT-LLM, NVIDIA Dynamo 등이 지원). 근거: prefill은 병렬 연산량이 많은 **compute-bound**, decode는 토큰 단위 순차 처리라 **memory-bound**로 성격이 정반대이므로, 각 단계를 특성에 맞는 하드웨어에 분리 배치하면 이득이 있다는 것.
- **다만 GenieX API로는 구현 불가**: `LlmCreateInput`은 `device_id`(HTP0/GPUOpenCL/CPU)와 `config.n_gpu_layers`(레이어 몇 개를 오프로드할지)로만 제어됨. `n_gpu_layers`는 **레이어 단위** 분할이라, 특정 레이어를 GPU에 배정하면 그 레이어는 prefill이든 decode든 항상 GPU에서 처리됨. "prefill 때는 GPU, decode 때는 NPU"처럼 **단계별로 백엔드를 전환하는 옵션은 노출되어 있지 않음.** 실제로 구현하려면 prefill 완료 후 KV 캐시를 추출해 다른 백엔드로 이관하는 저수준 커스텀 작업이 필요 — Tier 3(raw QNN NDK)보다도 깊은 범위.
- **단, 부분적으로는 이미 실험 설계에 포함되어 있음**: 2장의 "디스패치 모드" 변인(hybrid vs pinned-HTP0)이 사실상 "여러 곳에 나눠 처리 vs 한 곳에서만 처리"를 테스트함. `device_id`를 지정하지 않으면(hybrid) llama.cpp가 **텐서(연산자) 단위로 HTP/CPU에 자동 분산**함. 다만 이는 *단계(phase)* 단위가 아니라 *연산자(op)* 단위 분산이라는 점에서 위 아이디어와는 층위가 다름.

**결론**: 연구 주제로서는 매력적이나 이번 실험 범위 밖. 논문/보고서 작성 시 "향후 과제(future work)" 절에 넣기 좋은 항목.

### 10-A-3. VELTAIR식 "레이어별 다중 버전 컴파일 + 적응형 스케줄러"를 GPU/NPU로 이식 — 개념적으로 유효하나 이번 학기 범위 밖 (2026-08-06 추가)

**배경**: "지금 계획은 파라미터만 바꿔서 최적값 찾는 것뿐이라 너무 단순한 것 아니냐"는 문제 제기에서 출발. 근거로 든 논문은 **VELTAIR**(ASPLOS 2022, arXiv:2201.06212, 원문 확인) — CPU 서버에서 여러 DNN 추론 요청이 동시에 돌 때 생기는 LLC/캐시 경합 문제를 풀기 위해, 레이어(op)마다 서로 다른 자원 사용 패턴(exclusive 자원 위주 vs shared 자원 위주)을 가진 코드를 복수 버전으로 컴파일해두고(TVM auto-scheduler를 확장한 single-pass multi-version search), 런타임에 현재 간섭도를 관측해 스케줄러가 매 순간 최적 버전 + 스케줄링 단위(동적 threshold 기반 레이어 블록)를 고르는 방식.

**결론**: 개념 자체는 GPU(Adreno)/NPU(Hexagon HTP) 양쪽에 이식 가능하고, 특히 이 프로젝트가 이미 발견한 두 가지와 정확히 맞물림 — ① QNN의 "Concurrent Resource Sharing"(V81/S26 Ultra 전용, 여러 그래프가 VTCM 등 공유자원을 나눠쓸 때의 최적화)이 VELTAIR가 다루는 문제(공유자원 경합)와 동일한 문제의식이라는 점, ② BL0~BL2 배경부하 실험에서 "유튜브 재생은 GPU 연산 자원을 실제로 뺏지 않고 메모리 대역폭/열예산만 건드린다"고 실측으로 이미 확인한 것 — 즉 이 프로젝트 환경에서의 경합은 VELTAIR가 다룬 서버 CPU의 LLC 경합보다 **공유 메모리 대역폭 경합**에 가까울 가능성이 높다는 점이, 이식 시 가장 먼저 검증해야 할 전제가 됨.

**계층별 이식 가능성**:

| VELTAIR 구성요소 | GPU(Adreno, MLC-LLM=TVM 기반) | NPU(Hexagon HTP, QNN/QAIRT) |
|---|---|---|
| 레이어별 다중 버전 코드 생성 | **가장 현실적** — MLC-LLM이 이미 TVM 기반이라 VELTAIR 원 논문과 같은 auto-scheduler 확장을 재사용할 여지가 있음(단, Adreno OpenCL 타깃으로 재검증 필요) | QAIRT는 그래프를 AOT로 통째 컴파일하는 구조라 "레이어" 단위가 아니라 "서브그래프" 단위로만 버전 분리 가능 — `VTCM_SIZE_IN_MB`/`NUM_HVX_THREADS`를 다르게 준 버전을 미리 여러 개 컴파일해두는 방식으로 흉내는 가능 |
| 런타임 경합도 모니터링 | Snapdragon Profiler GPU 클럭/사용률 카운터, ADPF | `profilerUtilityApp`의 DSP 카운터(Bus Clock Vote 등, S26 Ultra 지원 확인됨) |
| 적응형 스케줄러(버전 선택 + 스케줄 단위 조정) | 직접 구현 필요(llama.cpp/MLC-LLM 런타임에 없음) | 직접 구현 필요 — Graph Priority/Performance Profile은 "이미 있는 정적 프로파일 중 택1"이라 방향은 같지만 컴파일 단계에서 새 버전을 만드는 건 아님 |

**왜 이번 학기 범위 밖인가**: VELTAIR 자체가 "컴파일러+스케줄러를 새로 만든" ASPLOS 논문 한 편 분량의 시스템 빌드 작업. 지금 계획은 이미 있는 API(GenieX Kotlin/QNN config)의 파라미터를 스윕하는 "측정" 프로젝트인데, 이 아이디어를 온전히 구현하면 "측정"에서 "시스템 빌드"로 프로젝트 성격 자체가 바뀌고, 12-3/12-4에서 이미 지적한 Tier 3(raw QNN NDK)보다도 훨씬 깊은 엔지니어링(TVM 커스텀 스케줄 튜닝, 런타임 코드 수정)이 필요함.

**절충안(제안, 시간 남으면 검토)**: "컴파일러를 새로 만들기"가 아니라 "이미 있는 정적 옵션들 중 실시간으로 고르는 정책"만 축소 검증.
- NPU: 고정된 HTP Performance Profile 하나로 20회 반복하는 기존 프로토콜 대신, ADPF thermal headroom/DSP 카운터를 관측해 반복 도중 profile을 전환하는 정책(A: 고정 vs B: 조건 기반 동적 전환)을 비교 — "코드 재생성" 없이 "적응형 스케줄링" 개념만 검증.
- GPU(선택): MLC-LLM이 TVM 기반이라는 점을 활용해 matmul/attention 등 핵심 레이어 한둘만 골라 실제로 2~3개 버전을 뽑고, GPU 클럭 신호로 전환하는 축소 프로토타입.

**관련 선행연구(교차검증)**: "Miriam: Exploiting Elastic Kernels for Real-time Multi-DNN Inference on Edge GPU"(arXiv 2307.04339)가 정확히 "엣지 GPU에서 커널을 여러 버전(elastic)으로 만들어 멀티-DNN 경합 상황에 런타임 선택"하는 동일 계열 아이디어를 이미 다룸 — VELTAIR를 모바일/엣지 GPU로 이식하는 방향이 학계에서도 유효한 시도임을 뒷받침. 다만 NPU(Hexagon HTP) 쪽에서 이 정확한 조합(다중 버전 컴파일+적응형 스케줄러)을 다룬 선행연구는 이번 조사에서 찾지 못함 — 시도한다면 novelty는 있으나 검증된 참고 사례가 없다는 리스크도 있음.

5. **(신규) 실기를 받았으면 가장 먼저 할 일**: Snapdragon Profiler를 데스크톱에 설치하고 USB로 S26 Ultra를 연결해 실제로 기기가 인식되고 카운터가 잡히는지 확인할 것. 지금까지의 "SM8850 지원" 판단은 전부 공식 문서 기반 정황 증거였고, 실기로 직접 검증되는 순간 이 계획의 마지막 불확실성이 사라짐.

## 12. 최종 종합 확인 — "실험을 막거나 불가능하게 하는 요소가 남아있는가?" (2026-08-04)

**결론부터: 지금까지 조사한 범위 안에서 실험 자체를 원천적으로 막는(=불가능하게 만드는) 요소는 없음.** 다만 "막는 것"과 "번거롭게/불확실하게 만드는 것"은 다른 문제라서, 남아있는 항목을 전부 등급을 나눠 솔직하게 정리한다.

### 12-1. 진짜로 실험을 막는 요소 — 없음

QDC 계정 승인 불확실성은 실기 확보로 해소됐고, 그 외에 "이래서 아예 불가능하다"고 판단할 근거는 이번까지의 조사에서 나오지 않았음.

### 12-2. 아직 실기로 직접 확인 안 된 것 (막을 가능성은 낮지만 0%는 아님)

- Snapdragon Profiler ↔ SM8850 실제 USB 연결/카운터 수집 — 공식 지원 칩셋 목록엔 있지만 실측 테스트는 아직 안 함(11-7에서 "가장 먼저 해볼 것"으로 이미 표시해둠).
- GenieX `ProfilingData`가 반환하는 정확한 필드 구성 — 공개 문서로 100% 확정 못함, 실행 후 로그로 직접 확인 필요.

### 12-3. 확실히 되지만 추가 작업량이 필요한 것 (막는 게 아니라 시간이 드는 것)

- Tier 3(Graph Priority, Performance Profile, VTCM, HVX threads)는 GenieX 공식 Kotlin API가 노출하지 않음 → raw QNN/QAIRT NDK(C++)를 직접 작성해야 하는, 앱 개발과 별개의 추가 엔지니어링 작업. "안 되는 것"이 아니라 "일정이 더 드는 것" — 학기 일정상 Tier 1~2 먼저 끝내고 여유 되면 확장 권장.
- `qairt` 경로는 context 길이가 컴파일 시점 고정 → 이 변수를 스윕하려면 조건별로 여러 바이너리를 미리 준비해야 함.

### 12-4. 소프트웨어 성숙도 리스크

GenieX는 공식적으로 "Developer Preview"(정식 출시 이전) 배지가 붙어 있고, 최근 2주 사이에도 버전이 올라감(문서 예시 0.3.1 → Maven Central 실측 0.3.16). 프리뷰 소프트웨어라 실험 도중 API나 동작이 바뀔 수 있음 — **실험 시작 시점에 사용 버전을 고정(pin)해서 끝까지 그 버전으로 진행할 것을 권장**.

### 12-5. 물리적·실무적 리스크 (이번에 새로 짚는 부분)

- **지급받은 기기라는 점**: 학교/연구실에서 이 실험 목적으로 대여·지급된 기기라면 MDM(기기 관리) 프로파일이 걸려 있어 "출처를 알 수 없는 앱" 설치나 개발자 옵션이 막혀 있을 수 있음. 이건 문서 조사로는 알 수 없는, 실기에만 있는 정보라 **설정 > 생체인식 및 보안 / 설정 > 기기 관리 앱**에 잠금 프로파일이 있는지 직접 확인이 필요함 — 문서 조사로 대신 확인해줄 수 없는 유일한 항목.
- 반복 벤치마킹(조건당 20회×3세트, 조건 사이 30분 냉각)은 실측상 조건 수에 따라 수 시간~하루 단위로 소요될 수 있음 — "불가능"이 아니라 일정을 넉넉히 잡아야 하는 문제.
- 장시간 고부하 반복 실험은 배터리 마모·발열 스트레스를 누적시킴 — 반납해야 하는 기기라면 이 점을 고려해 조건 수/반복 수를 조절할 것.

### 12-6. 결론

막는 요소는 없음. 남은 건 전부 "실기로 그 자리에서 몇 분 안에 확인 가능한 것"(Profiler 연결, 필드명) 아니면 "시간·개발량이 드는 것"(Tier 3 NDK)이지 "안 되는 것"은 아니다. 문서 조사로 대신 확인할 수 없고 사용자가 직접 봐야 하는 항목은 딱 하나 — 지급받은 기기에 MDM 제약이 걸려 있는지 여부.

## 13. 배경 부하 재설계 — 삼성 관점 정렬(Galaxy AI 실사용 시나리오) (2026-08-06 추가)

**배경**: "지금 계획이 퀄컴 칩 성능 얘기에 가깝지, 삼성이 흥미로워할 이야기는 아니지 않냐"는 문제 제기에서 출발. 삼성은 HTP(Hexagon)/Adreno 같은 실리콘을 직접 설계하지 않으므로(이 프로젝트가 다루는 스냅드래곤 갤럭시 한정 — 자체 GPU/Exynos NPU는 별도 트랙), 삼성이 실제로 통제·마케팅하는 층위는 **온디바이스 Galaxy AI 기능 자체와, 그 기능들이 동시에 실행될 때의 UX**다. 2026-02 S26 언팩 공식 발표에서 "NPU 39% 향상, CPU 19% 향상으로 여러 작업이 동시에 실행돼도 지연 없이 처리"라고 명시했고, 이번 언팩은 "agentic AI"(다단계 자율 작업)를 핵심으로 내세웠다. 즉 삼성이 지금 파는 약속은 정확히 "Galaxy AI 여러 개가 동시에/연쇄적으로 돌아도 안 밀린다"는 것 — 이 약속을 검증/반박하는 실험이 기존 6-4(일반 백그라운드 앱 기반 BL0~BL3)보다 삼성의 실제 관심사에 훨씬 부합한다.

### 13-1. 새 연구질문(RQ7)

**RQ7**: 백그라운드 부하를 일반 앱이 아니라 **삼성 자사 온디바이스 Galaxy AI 기능**으로 한정했을 때,

1. 벤치마크(우리가 돌리는 LLM) 처리량이 얼마나, 어떤 조건에서 저하되는가?
2. 그 저하는 대칭적인가 — 즉 Hexagon NPU 스케줄러가 삼성 1st-party 프로세스와 서드파티(우리) 프로세스를 동등하게 취급하는가, 아니면 삼성 자사 프로세스에 우선순위가 주어지는가? (QAIRT 공식 문서의 Graph Priority/cooperative preemption 메커니즘이 실제로 이렇게 쓰이는지 실측으로 확인하는 셈 — 공개된 적 없는 실측치라 임팩트가 큼)
3. 삼성이 프라이버시 명목으로 제공하는 "기기에서만 처리" 강제 토글이 성능을 얼마나 희생시키는가?

### 13-1-A. 독립변인 · 종속변인 · 발견목표 정리 (2026-08-06 추가)

**독립변인(통제변인)**

| 변인 | 수준 |
|---|---|
| BLG 레벨 | BLG0(없음) / BLG1(오브젝트 지우개) / BLG2(문서스캔) / BLG3(통역) / BLG4(에이전틱, 선택) |
| "기기에서만 처리" 토글 | ON / OFF |
| compute unit(기존 6-1 유지) | NPU-hybrid / NPU-pinned / GPU / CPU / qairt(조건 A~E) |
| 반복 횟수 | 1~20회(열 상태의 대리 변수) |

**종속변인(측정 항목)** — 기존 3장 항목에 "삼성 쪽" 응답시간이 새로 추가됨

- 우리 쪽: tok/s, TTFT, prefill/decode time, 배터리 온도·전류(3장과 동일)
- 삼성 쪽(신규): Galaxy AI 기능 자체의 처리 완료 시간 — 예: 오브젝트 지우개가 **BLG1 혼자 돌 때**(우리 벤치마크 없이) 걸리는 시간 vs **우리 벤치마크와 동시에** 돌 때 걸리는 시간. RQ7-2(비대칭성)를 답하려면 이 쌍을 반드시 같이 재야 함.

**발견목표(가설)** — 종속변인 수치 자체가 아니라 그로부터 내리고 싶은 결론

1. Galaxy AI 기능이 켜져 있으면 우리 LLM 처리량이 떨어지는가, 얼마나(RQ7-1, 확인형 질문).
2. **핵심**: 그 저하율이 우리 앱과 삼성 앱 양쪽에 비슷하게 나타나는가, 아니면 우리만 불균형하게 더 느려지는가 — 후자면 "삼성이 자사 프로세스에 NPU 스케줄링 우선순위를 실제로 준다"는 실측 근거(RQ7-2, 지금까지 공개된 적 없어 보이는 발견 지점 — 1·3번이 "얼마나"를 묻는다면 이건 "왜/불공평하게"를 캐는 질문이라 성격이 다름).
3. "기기에서만 처리" 토글의 성능 비용 — 삼성의 "프라이버시가 성능을 깎지 않는다"는 암묵적 약속이 실제로 맞는지(RQ7-3).

### 13-2. 기기 범위 — S26 Ultra 한정

이 축은 **S26 Ultra에서만 유효**하다. Samsung 공식 발표(One UI 6.1 확장 발표)에 "온디바이스 Galaxy AI 기능은 최신 NPU가 필요하고, 그렇지 않은 기기는 대부분 클라우드로 처리된다"고 명시돼 있음 — S22/Fold4/Flip4(HTP v69, 8 Elite 미만)는 Galaxy AI 기능 자체는 One UI 6.1로 들어왔어도 온디바이스 NPU 경로가 아니라 클라우드 폴백일 가능성이 높아 "온디바이스 NPU 자원 경쟁"이라는 이 실험의 전제가 성립하지 않는다. 세 구형 기기는 기존 8-6/9-6의 "폼팩터별 스로틀링 비교" 트랙을 그대로 유지 — 이건 이것대로 삼성의 하드웨어 설계(방열·힌지) 영역이라 별개로 유효하다.

### 13-3. BLG(Galaxy AI 배경부하) 매트릭스 — 기존 6-4의 BL0~BL3을 대체/보강

| 레벨 | 시나리오 | 온디바이스 근거 | 자동화 난이도 | 비고 |
|---|---|---|---|---|
| BLG0 | 기준(Galaxy AI 미사용) | — | 낮음 | 기존 BL0와 동일 |
| BLG1 | 설정 > Galaxy AI > "기기에서만 처리" 강제 ON + 갤러리 고정 사진에 AI 지우개(오브젝트 지우기) 반복 적용 | 공식: 온디바이스 편집(클라우드 없이) | 낮음~중간(토글 1회 + 좌표 반복 탭) | **재현성 가장 높음, 첫 실험으로 권장** |
| BLG2 | Document Scan으로 고정 거치된 문서 반복 촬영 | 공식 사례에서 온디바이스로 언급 | 중간(카메라 프레이밍 고정 필요) | |
| BLG3 | Interpreter(양방향 통역) 실행 후 반복 재생 오디오 노출 | Live Translate/Interpreter가 프라이버시 목적 온디바이스로 마케팅됨 | 중간~높음 | Live Translate는 실통화가 필요해 자동화 어려움 → Interpreter로 대체 권장 |
| BLG4(선택) | 에이전틱 AI 멀티스텝 작업 트리거 후 진행 중 관측 | 2026 언팩 핵심 발표 | 높음(트리거 방법 자체 미확정) | 정성적 비교만, 시간 남으면 |

부가 통제변인(2수준): **"기기에서만 처리" 토글 ON/OFF** — ON이면 클라우드 폴백을 차단해 100% 로컬 NPU 경쟁을 보장(재현성↑, 단 일부 기능 품질 저하는 삼성도 인정하는 트레이드오프). OFF면 기본 하이브리드(네트워크 상태에 따라 결과가 흔들려 재현성↓이지만 실사용에 더 가까움). 이 토글 자체를 스윕하면 "삼성이 프라이버시 모드를 성능 손해 없이 제공하는가"를 정량화할 수 있어 그 자체로 흥미로운 결과.

### 13-4. 분석 계획 — 비대칭성(fairness) 검증

각 BLG 조건에서 (a) 우리 벤치마크 앱의 tok/s 저하율과 (b) 가능하다면 Galaxy AI 기능 자체의 체감 응답속도(예: Document Scan 처리 완료까지 걸리는 시간) 저하율을 나란히 기록. 만약 우리 앱만 불균형하게 느려진다면 "삼성 1st-party 프로세스에 스케줄링 우선순위가 실제로 주어진다"는 실측 근거가 되고, QAIRT 공식 문서의 Graph Priority(cooperative preemption) 메커니즘이 실제로 그렇게 동작하는지를 보여주는 셈 — 지금까지 조사한 범위에서 이 비교를 직접 실측한 공개 자료는 찾지 못했다.

### 13-5. 리스크·한계 (정직하게 명시)

- **BL2(유튜브)가 실제로는 GPU를 안 썼다는 2-4의 교훈이 여기도 그대로 적용될 수 있음**: Document Scan·오브젝트 지우개 등이 정말 메인 Hexagon HTP0(우리 LLM 벤치마크와 같은 물리 유닛)를 쓰는지, 아니면 별도의 저전력 상시감지용 서브블록(9-3에서 이미 확인한 "Sensing Hub Dual Micro NPU"류, 일반 워크로드 대상 아님)을 쓰는지는 실기에서 Snapdragon Profiler DSP 카운터로 먼저 확인해야 함 — 확인 전까지는 가설.
- 반복 트리거 자동화(사진 20회 편집, 문서 20회 촬영 등)는 UI 자동화(adb 탭 좌표 스크립트 또는 UiAutomator)가 필요 — Kotlin API 호출 한 줄이 아니라 별도 스크립팅 작업(대략 반나절~하루 추정).
- "기기에서만 처리" 토글이 실제로 어느 기능까지 적용되는지 One UI 8.5 설정 화면에서 실기로 직접 확인 필요 — 문서상 일부 기능은 토글과 무관하게 항상 클라우드일 수 있음.
- 에이전틱 AI(BLG4)는 출시 직후 기능이라 재현 가능한 트리거 방법 자체가 조사 단계에서 확정되지 않음 — 시간 여유 있을 때 실기로 먼저 탐색.
- Interpreter/Document Scan이 반복 실행 중 자체적으로 쿨다운·요청 제한(rate limit)을 두는지도 미확인 — 있다면 20회 반복 프로토콜과 충돌 가능.

### 13-6. 기존 6-4(BL0~BL3, 일반 앱 기반)와의 관계

대체가 아니라 **선행 파일럿 vs 본실험**으로 배치 권장: 6-4(유튜브/음악)는 이미 "일반 백그라운드 앱은 GPU/NPU 연산을 실제로 못 뺏는다"는 부정적 결과가 나온 파일럿으로 취급하고, 보고서에는 "그래서 진짜 경쟁 상대(Galaxy AI 자사 기능)로 좁혔다"는 서사로 연결. 시간이 부족하면 BLG1(가장 재현성 높음) 하나만이라도 BLG0 대비 비교해 RQ7-1(저하 여부)에 답하고, 이후 여유 되면 RQ7-2(비대칭성)로 확장.

## 14. 문제 해결 시도 — 적응형 백엔드 디스패처 제안 (2026-08-06 추가)

**배경**: RQ7-2(삼성 1st-party 프로세스가 NPU 스케줄링에서 우대받는가)를 "발견"만 하지 말고, VELTAIR·Miriam·Puzzle 같은 선행연구들이 그랬듯 우리도 완화책을 만들 수 있는지 검토. 이 논문들의 공통 레시피는 **"경합을 감지하는 모니터 + 그에 따라 자원/버전을 바꾸는 정책"** — 이를 훨씬 가벼운 앱 레벨 버전으로 이식.

**제약 재확인**: 10-A-2에서 이미 결론 낸 대로, GenieX API는 **추론 도중** prefill/decode처럼 스트림 중간에 백엔드를 전환하는 걸 지원하지 않음(KV 캐시를 다른 백엔드로 이관해야 해서 Tier 3보다도 깊음). 그래서 "스트림 중 전환"은 포기하고, **매 요청(턴) 시작 시점에 배정을 결정**하는 방식으로 스코프를 좁히면 기존 API(Tier 1)만으로 구현 가능.

### 14-1. 제안: 요청 단위 적응형 백엔드 디스패처

1. 새 추론 요청 직전, 최근 decode step 지연시간(이동평균) 또는 ADPF thermal headroom을 관측해 "지금 NPU가 붐비는가" 판단.
2. 붐비면 해당 요청은 GPU/CPU로, 한가하면 NPU로 — `compute_unit`만 바꿔 요청 단위로 배정(GenieX Kotlin API가 이미 지원, Tier 1).
3. 비교군: 정적 NPU-only / 정적 GPU-only / 적응형 디스패처 — 셋을 BLG1~4 아래에서 동일 프로토콜로 비교.

**기대 결과(가설)**: 평균 처리량은 정적 NPU-only와 비슷하거나 약간 낮아도, **지연시간 변동성(표준편차·최악값/tail latency)**은 줄어들 것 — VELTAIR도 평균보다 QoS(안정성) 개선을 핵심 성과로 제시했던 것과 같은 틀로 보고.

### 14-2. 확장(선택, Tier 3) — 회피 대신 정면 승부

디스패처로 자원을 피하는 대신, 우리 그래프의 **HTP Graph Priority를 명시적으로 상향**해서 RQ7-2에서 발견한 격차가 줄어드는지 테스트. raw QNN NDK 필요 — 순서상 14-1 이후, 시간 남으면.

### 14-3. 순서 및 한계

- **선측정 후해결**: RQ7-2로 비대칭이 실제로 있는지부터 확인하고, 확인되면 그때 디스패처 효과를 검증. 문제가 없으면 해결책도 의미 없음.
- 프로브 자체가 오버헤드를 만들어 측정을 오염시킬 수 있음(관측이 곧 간섭) — 프로브 비용 최소화 필요.
- 한 요청(턴) 안에서는 반응 못 함 — 턴 단위로만 재배정되므로, 긴 스트리밍 응답 중간의 경합 변화에는 대응 불가(이 한계는 명시하고 넘어갈 것).
- 이 확장 전체는 12-3/12-4에서 이미 지적한 "시간 부족" 우려에 걸리므로, 정식 매트릭스가 아니라 시간 남으면 진행하는 선택 확장으로 배치.

### 15-1. BLG 관련 리스크

BLG는 설정값 하나를 바꾸는 게 아니라 삼성 자사 앱(갤러리/카메라/통역)의 UI를 좌표 탭으로 흉내내는 방식이라 통제력이 compute_unit·토글보다 훨씬 약함. 또한 안드로이드는 포그라운드 앱이 하나뿐이라 우리 벤치마크와 Galaxy AI 기능을 동시에 돌리려면 split-screen이 필요한데(2-4에서 유튜브 때 쓴 방법과 동일), **Document Scan처럼 카메라 라이브뷰가 필요한 기능은 split-screen/비포커스 상태에서 정상 동작하는지 미확인** — 이는 BL2(유튜브)가 "화면에 안 보이면 디코딩을 줄인다"고 실측으로 걸렸던 함정과 같은 패턴이라 반복 위험. 반대로 **BLG1(오브젝트 지우개)은 카메라 라이브뷰가 필요 없는 일회성 버튼 작업이라 이 문제에서 자유로움** — 13-3에서 BLG1을 첫 실험으로 권장한 이유가 이 재검증으로 보강됨.

### 15-2. 14장 디스패처 관련 리스크(신규 발견)

GenieX의 `compute_unit`은 모델 로드 시점(`LlmCreateInput`) 파라미터로 보여, 요청마다 전환하려면 모델을 통째로 재로드해야 할 가능성이 있음(수 초 단위 비용이면 "가벼운 적응형 정책"이라는 전제가 깨짐). 대안은 NPU/GPU/CPU 세 세션을 앱 시작 시 모두 미리 로드해두고 요청마다 라우팅만 바꾸는 구조인데, **GenieX가 한 프로세스에서 여러 세션을 동시에 유지할 수 있는지는 지금까지 조사로 확인되지 않음**.

### 15-3. 결론 및 다음에 확인할 것

지금 자신 있게 "조정 가능"이라 말할 수 있는 건 compute_unit·"기기에서만 처리" 토글·반복 횟수뿐. BLG 트리거, BLG-벤치마크 동시실행, 14장의 요청 단위 세션 전환은 전부 "이론상 되어야 하는데 실기 검증이 안 된" 상태 — 다음 세션에서 실기로 우선 확인할 항목:

1. Document Scan/카메라 기반 기능이 split-screen에서 정상 동작하는지(안 되면 BLG2는 BLG1·BLG3로 대체).
2. GenieX가 한 프로세스에서 NPU/GPU/CPU 세 세션을 동시에 로드할 수 있는지, 안 되면 compute_unit 재로드 비용이 실제로 몇 ms/초인지.
3. "기기에서만 처리" 토글의 정확한 설정 경로와 적용 범위.

## 16. GenieX 대안 프레임워크 및 관련 최신 논문 탐색 (2026-08-06 추가)

**배경**: 15장에서 걸린 두 리스크(BLG-벤치마크 동시실행의 포그라운드 충돌, 요청 단위 세션 전환 비용)가 GenieX API 자체의 한계일 수 있어 대안 프레임워크를 탐색.

### 16-1. 대안 프레임워크 비교

| 프레임워크 | NPU 지원 | 다중 세션/백엔드 동시 로드 | 헤드리스 실행(포그라운드 불필요) | 성숙도 |
|---|---|---|---|---|
| GenieX(현재 계획) | O(QAIRT) | 미확인, Tier1 API 제한적 | X(GUI 앱) | Developer Preview |
| **llama.cpp(Hexagon 백엔드)** | O(HTP0-4, `D=`플래그) | 프로세스 여러 개 띄우면 됨 | **O — adb로 백그라운드 실행 가능** | Experimental이나 공식 병합됨(10-A-1) |
| **ExecuTorch**(Meta/PyTorch) | O(Qualcomm QNN, Hexagon+Adreno, XNNPACK CPU) | 백엔드별 `.pte` export, 오픈소스라 Module 인스턴스를 직접 여러 개 관리할 여지 있음(공식 문서는 "폴백" 중심 설명, 진짜 동시실행은 실기 확인 필요) | 가능(자체 앱으로 구현 시) | 활발히 개발 중(2026 릴리스, Qwen3.5/Gemma4/Llama4 지원) |

| LiteRT-LM(MediaPipe 후속) | NNAPI 경유 주장(속도 배수는 출처 신뢰도 낮음) | 미확인 | 미확인 | 신규, 문서 부족 |

**권장**: 코어 Tier1~2 측정(6장)은 GenieX 그대로 유지. 13~15장(BLG/디스패처) 실험은 llama.cpp Hexagon CLI로 전환 권장 — `adb shell` 백그라운드 실행이 되므로 15-1의 포그라운드 충돌 문제가 근본적으로 사라짐. 14장 디스패처(세션 동시 로드)는 ExecuTorch가 유력 — 오픈소스라 GenieX 블랙박스보다 직접 제어 여지가 큼, 단 동시 로드 가능 여부는 실기 확인 필요.

### 16-2. 관련 최신 논문 3편

- **ShadowNPU**(MobiSys 2026, arXiv:2508.16703) — "다른 일반 앱(CPU/GPU 쓰는 UI·렌더링)과의 자원 경합을 피하려 LLM 추론을 최대한 NPU 안에 가둔다"는 RQ7과 동일한 문제의식이나, 해법 철학은 정반대. 우리 14장은 "경합 감지 시 NPU에서 회피(GPU/CPU 전환)"인데, ShadowNPU는 희소 어텐션(shadowAttn)으로 attention 연산의 CPU/GPU 폴백 자체를 없애 "NPU에 눌러앉는" 접근. 보고서에서 "회피형(우리) vs 고수형(ShadowNPU)" 대조 근거로 인용 가치 있음.
- **"Is Your NPU Ready for LLMs?"**(2026-07, arXiv:2607.05475) — prefill=NPU 유리, decode=CPU 유리라는 phase-aware 스케줄링·백엔드 선택을 제안. 10-A-2에서 "GenieX로는 단계별 백엔드 전환 불가"로 접었던 아이디어가 최신 연구에서 실제로 다뤄지는 중 — ExecuTorch 등 오픈소스 경로로 재검토 여지.
- **"Fast On-device LLM Inference with NPUs"**(ASPLOS'25) — "보통 GPU가 NPU보다 다른 앱들과 자원 경합이 더 심하다"는 관찰. RQ7 가설과 반대 방향 힌트라 "NPU보다 GPU 경로에서 더 큰 저하가 나올 수 있다"는 대안 가설로 BLG 매트릭스에 반영 고려.

**참고**: 이 세 논문 모두 원문 전체를 정독하지 않고 검색 요약 기반으로 정리함 — 실제 인용 전 원문 확인 필요(arXiv 링크는 검색 결과에 포함됨).

## 17. Galaxy AI 사용/프라이버시/기기상태 통합 매트릭스 (2026-08-06 추가)

**배경**: "Galaxy AI 사용 중 우리 LLM 성능 비교", "프라이버시 모드 켜고 AI 사용 중 비교", "이 둘을 배터리·절전모드·백그라운드 앱 등 기기상태별로도 측정"이라는 요청. 세 축(BLG, 프라이버시 토글, 폰 상태)을 전부 풀 팩토리얼로 곱하면 수백 조건이 되므로, 필수 축과 교차-확인 축을 나눠 스코프를 줄임.

### 17-1. 1단계(필수) — Galaxy AI × 프라이버시 3조건

| 조건 | 상태 |
|---|---|
| G0 | Galaxy AI 미사용(기준) |
| G1 | Galaxy AI 사용 + "기기에서만 처리" 토글 OFF(기본 하이브리드) |
| G2 | Galaxy AI 사용 + "기기에서만 처리" 토글 ON(강제 온디바이스) |

compute_unit은 NPU-hybrid(6-1 조건 A) 1개로 고정 — 안 그러면 3×5=15조건부터 시작하게 됨. G1/G2는 13-3의 BLG1(오브젝트 지우개, 재현성 최고)로 구현. 규모: 3조건×20회×3세트=**180회**.

### 17-2. 2단계(교차-확인, 시간 되면) — 폰 상태 축

G0/G1/G2는 "기준 상태"에서만 먼저 재고, 가장 대표적인 시나리오(G1, 프라이버시 토글 안 켜고 그냥 쓰는 기본값) 하나만 골라 아래 폰 상태를 추가로 교차.

| 폰 상태 조건 | 내용 |
|---|---|
| P0(기준) | 배터리 80%+, 전원모드=고성능, 백그라운드 앱 없음 |
| P1 | 배터리 저잔량(20% 미만) |
| P2 | 전원모드=절전 |
| P3(선택) | 기타 백그라운드 앱(BL1=음악. 유튜브=BL2는 2-4에서 이미 GPU 효과 없음 확인됨, 제외) |

**배터리 저잔량 통제 방법**: 실제 방전은 시간이 오래 걸리므로 `adb shell dumpsys battery set level <n>`으로 표시 잔량을 시뮬레이션하는 방법이 있음 — 단, 이게 실제 절전/스로틀링 동작까지 트리거하는지(표시값만 바뀌고 내부 전력관리는 그대로일 가능성)는 **실기 확인 필요**, 확인 전까지는 가정.

규모: G1 × P0~P3 4조건 × 20회 × 3세트 = **240회 추가**(1단계 180회 포함 총 420회). 3×4 풀 조합(12조건×60=720회)보다 현실적인 축소판.

### 17-3. 리스크·한계

- compute_unit·BLG·프라이버시·폰상태 4개 축을 전부 곱하지 않고 일부만 고정한 설계라, "NPU-hybrid + G1(토글 OFF)" 조합 밖의 상호작용(예: GPU 경로에서는 프라이버시 토글 효과가 다를 수 있음)은 이번 설계로는 못 봄 — 보고서에 명시할 것.
- `dumpsys battery set level`의 실제 스로틀링 유발 여부 미확인(위 참고).
- 절전모드(전원모드=절전)가 CPU 클럭 상한을 거는 건 8-3에서 이미 확인됐으나, NPU/HTP 클럭에도 동일하게 적용되는지는 별도 확인 필요.

## 18. 17장 실행 가능성·삼성 효과 재검토 (2026-08-06 재확인)

### 18-1. 새로 발견한 문제 — BLG1(오브젝트 지우개) 선택 자체가 흔들림

13-3에서 재현성이 가장 높다고 첫 실험으로 추천했던 BLG1(오브젝트 지우개)이, 삼성 커뮤니티 다수 게시물에 따르면 **최근 One UI 업데이트(우리 S26 Ultra가 쓰는 정확히 그 버전, One UI 8.5)에서 온디바이스 → 클라우드 전용으로 바뀌었다**는 사용자 불만이 확인됨. 즉 이 기능은 더 이상 온디바이스 NPU 부하를 안 만들 수 있음 — **BL2(유튜브)에 이어 같은 함정(겉보기엔 로컬 부하 같지만 실제로는 아님)에 세 번째로 걸릴 뻔함.**

Galaxy AI 기능 재분류(검색 재확인):
- **완전 온디바이스**(Call Screening 등) — 토글과 무관하게 항상 로컬 → G1/G2가 구분 안 됨(같은 조건이 됨)
- **하이브리드/로컬우선**(Now Nudge, Now Brief, Scam Detection) — 토글에 따라 실제로 차이 날 유일한 후보. 그런데 전부 **사용자가 직접 트리거하기 어려운 수동적/맥락 기반 기능**(시스템이 알아서 띄우거나, 실제 스팸 전화/문자가 와야 발동) — 20회 반복 프로토콜에 넣기 어려움
- **클라우드 의존**(Circle to Search, Creative Studio, Gemini) — 토글 ON이면 기능 자체가 비활성화될 수 있음 → "느려짐"이 아니라 "작동 안 함"으로 나타날 위험

**결론**: 지금 시점에 G1 vs G2(프라이버시 토글 비교)를 자동화된 반복 프로토콜로 깔끔히 실행할 수 있는 검증된 기능 후보가 없음. "시간이 드는" 문제가 아니라 "적절한 실험 대상을 아직 못 찾은" 더 근본적인 문제. **다음 세션 최우선**: 실기로 설정 > Galaxy AI를 열어 기능 목록과 토글 적용 범위를 하나하나 직접 확인.

### 18-2. 삼성 효과 재평가 — 톤 조정 필요

- "삼성이 흥미로워할 것"은 "삼성이 모르는 새로운 사실을 발견한다"보다 **"삼성의 공개 마케팅 주장(멀티태스킹 문제없음, 프라이버시가 성능을 안 깎음)을 외부에서 독립적으로 검증한다"**는 의미로 재정의하는 게 정직함. 삼성은 사내 QA로 이런 경합을 이미 훨씬 정교하게 테스트했을 가능성이 높음.
- RQ7-2(삼성 자사 프로세스 우대 여부)에서 만약 실제로 우대가 확인되면, 이는 **삼성이 반길 결과가 아니라 삼성에 비판적일 수 있는 결과** — "삼성이 흥미로워할 주제" ≠ "삼성에 유리한 결과가 나올 주제". 보고서 톤에서 이 구분을 분명히 할 것.
- **기기 1대(n=1)** 한정 실험이라 통계적 일반화는 어려움 — "사례 연구(case study)" 수준으로 프레이밍해야 함. 6장 base 실험(compute_unit 스윕)도 동일 기기 1대 한정이라 같은 한계가 있음(기존에 명시적으로 짚은 적은 없었으나 여기서 같이 확인).
- 그럼에도 남는 가치: ① 실사용 시나리오 기반 벤치마킹(BLG 기반)이 기존 6-4(일반 앱)보다 방법론적으로 실사용에 더 가깝다는 것 자체, ② 프라이버시 토글의 성능 비용 정량화는 삼성이 공개하지 않는 트레이드오프라 소비자 관점에서 실질적 정보 가치가 있음. 이 두 가지는 재검토 후에도 유효.

### 18-3. G1/G2 대체 후보 — 노트 어시스트 번역(미확인, 다음 세션 실기 검증 필요)

삼성은 노트 어시스트 번역을 "온디바이스 AI 기술 기반, 클라우드 안 거침"이라 설명하지만, 오브젝트 지우개도 과거 동일하게 설명되다 최근(One UI 8.5) 클라우드로 전환된 전례가 있어(18-1) 액면 그대로 신뢰 불가.

**단서**: 기본 언어(영어/한국어) 외 언어는 오프라인 번역을 쓰려면 **언어팩을 미리 다운로드**해야 한다는 공식 설명 확인. 추정 구조(미검증):
- 토글 OFF: 언어팩 없는 언어도 조용히 클라우드로 처리될 가능성
- 토글 ON("기기에서만 처리"): 클라우드 불가 → 언어팩 있으면 로컬 강제 처리(진짜 온디바이스 부하), 없으면 실패/다운로드 요구

**검증 방법(다음 세션)**: 언어팩 미다운로드 언어로 노트 번역 반복 시도 → 토글 ON/OFF 시 동작 차이 관찰, 비행기 모드에서도 되는지 확인(진짜 온디바이스인지 판별). 확인되면 BLG1(오브젝트 지우개, 18-1에서 신뢰성 흔들림)의 유력한 대체/추가 후보.

**(2026-08-06 실기 확인, 가설 기각)**: 사용자가 실기로 직접 확인 — **클라우드 허용(토글 OFF) 상태에서도 언어팩 다운로드를 요구함.** 즉 언어팩 요구는 토글과 무관 — "토글 OFF면 언어팩 없이도 클라우드로 조용히 처리될 것"이라는 위 가설은 기각됨. 오히려 이 결과는 번역 기능이 **토글과 무관하게 항상 로컬 언어팩(사전/모델)을 필요로 한다**는 쪽에 가까움 — 오브젝트 지우개(18-1)·Call Screening(완전 온디바이스)처럼 G1/G2 구분에는 못 쓸 가능성이 높아짐.

**다음 확인 단계**: ① 언어팩을 실제로 받아둔 뒤 **비행기 모드**에서 번역이 되는지 확인(되면 진짜 온디바이스 확정). ② 언어팩 확보 상태에서 토글 ON/OFF가 속도·동작에 차이를 주는지 비교. 차이가 없다면 이 기능은 G0(AI 미사용) vs G1(AI 사용) 비교에는 계속 쓸 수 있으나, **G1 vs G2(프라이버시 토글) 축의 후보에서는 제외**해야 함.

**(2026-08-06 갱신)**: 프라이버시 토글 축 자체를 19장에서 폐기했으므로, 이 기능은 토글 구분과 무관하게 N축(19장) 후보로 재검토됨 — 비행기모드 온디바이스 확인만 통과하면 N3 후보로 유효.

## 19. 설계 단순화 — 프라이버시 토글 제거, "Galaxy AI 동시사용 개수" 기반으로 전환 (2026-08-06 확정)

**결정**: 18장에서 프라이버시 토글(G1 vs G2)을 신뢰성 있게 구분할 Galaxy AI 기능 후보를 못 찾음(오브젝트 지우개=클라우드 전환 의심, 노트 번역=토글 무관하게 언어팩 항상 요구). 이에 따라 **토글 축을 폐기**하고, 13-1-A/17장의 "기기에서만 처리 토글" 행과 17장 전체의 G0/G1/G2 매트릭스는 이 장으로 대체됨.

**새 설계**: Galaxy AI 기능을 "어떤 기능이냐"가 아니라 **"몇 개를 동시에 쓰느냐"**로 축을 단순화. 종속변인은 기존 13-1-A대로 이원화 유지 — 우리 LLM 벤치마크 성능 + Galaxy AI 기능 자체("다른 AI", 우리 LLM 제외)의 응답성. "최적의 성능 찾기"는 두 갈래:

(a) 각 부하 수준에서 우리 LLM에 가장 유리한 compute_unit/설정을 찾는다.
(b) Galaxy AI를 동시에 몇 개까지 써도 성능 저하가 감내할 만한지 임계점(sweet spot)을 찾는다.

### 19-1. 새 독립변인 — Nx(동시 사용 개수)

| 조건 | 상태 | 사용 기능(제안) |
|---|---|---|
| N0 | Galaxy AI 미사용(기준) | — |
| N1 | 1개 사용 중 | Document Scan(BLG2) 또는 Interpreter(BLG3) — 오브젝트 지우개(BLG1)는 18-1에서 클라우드 전환 의심으로 1순위에서 제외 |
| N2 | 2개 동시 사용 | Document Scan + Interpreter 동시 실행 |
| N3(선택) | 3개 이상 동시 사용 | 노트 번역(18-3, 비행기모드로 온디바이스 확정된 경우에 한해) 추가 |

compute_unit은 목표 (a)를 제대로 답하려면 6-1의 A~E와 교차해야 함(시간 되면). 여유 없으면 NPU-hybrid(A) 하나로 고정.

### 19-2. 종속변인(13-1-A와 동일 구조 유지)

- 우리 쪽: tok/s, TTFT, prefill/decode time
- Galaxy AI 쪽("다른 AI", LLM 제외): 각 기능이 단독으로 돌 때 걸리는 처리시간 vs N1/N2에서 우리 벤치마크와 동시에 돌 때 걸리는 처리시간 — 자동 로그 접근 불가하므로 수동 스톱워치 측정 필요.

### 19-3. 분석 계획

- 목표(a): compute_unit × N수준 표로 정리 — N이 커질수록 어느 backend가 가장 덜 흔들리는지 확인. 예를 들어 N2에서 GPU가 NPU보다 나아지는 지점이 있으면 그게 "최적 설정"의 실질적 답.
- 목표(b): N0→N1→N2(→N3)로 갈수록 우리 LLM 처리량과 Galaxy AI 응답시간이 각각 얼마나 나빠지는지 곡선을 그려, 저하율이 급격히 꺾이는 지점을 sweet spot으로 보고.

### 19-4. 리스크

- N2(2개 동시)는 서로 다른 삼성 앱 두 개를 동시에 자동화해야 해서, 15/18장에서 이미 걸린 "기능 하나 자동화하기도 어려움" 문제가 배가됨 — N1까지 먼저 검증하고 N2는 시간 되면 확장 권장.
- Galaxy AI 응답시간은 수동 스톱워치로 잴 수밖에 없어 측정 노이즈가 큼 — 반복 횟수를 늘리거나 오차 범위를 명시할 것.
- N1 후보(Document Scan/Interpreter)도 "진짜 온디바이스인지"는 아직 실기 미확인 — 18-1과 같은 패턴이 반복될 위험이 있어 **다음 세션 최우선 확인 항목**.

## 20. 모델 다양성 및 "우리 측" 다중모델 동시실행 (2026-08-06 추가)

### 20-1. LLM 외 모델 종류 확장 — CNN/ResNet/VLM 전부 가능

Qualcomm AI Hub 확인(300+개 모델, Hexagon NPU/Adreno GPU/CPU 배포 지원):
- **CNN/ResNet**: ResNet18/50 등 다수 등록, QNN 공식 지원. YOLOv8과 동급 — 가볍고 HTP v69~v81 전체 지원.
- **VLM**: Qwen2.5-VL-7B-Instruct, Qwen3-VL 등 Hexagon NPU 배포 확인됨. 다만 7B급이라 LLM만큼 무거움 — 8 Elite+(S26 Ultra) 한정일 가능성 높음(GenieX와 동일한 제약 예상, 실기·문서 재확인 필요).

**기기별 모델 티어**:

| 모델 유형 | 예시 | 지원 범위 |
|---|---|---|
| 경량 CNN | ResNet18/50, YOLOv8, MobileNet | HTP v69~v81 전부 — S22/Fold4/Flip4/S26 Ultra 전 기기 |
| LLM | Qwen 계열(GenieX) | v81(qairt) 공식, 나머지는 비공식 |
| VLM | Qwen2.5-VL, Qwen3-VL | LLM급 무게, S26 Ultra 한정 추정(미확인) |

→ **경량 CNN을 쓰면 GenieX 제약으로 S26 Ultra에 갇혀 있던 13~19장 실험(BLG/Nx)을 구형 기기 3대까지 확장 가능**해짐.

### 20-2. "우리 측" 다중모델 동시실행 — 가능, 원래 Hailo 프로젝트 구조 재현

SNAPDRAGON_FEASIBILITY.md 2-2에서 이미 확인: **다중 모델 동시 실행 자체는 전 기기에서 가능**, "Concurrent Resource Sharing"(자원 공유 최적화)만 V81(S26 Ultra)에서 공식 지원 — 구형 기기(v69)도 여러 그래프를 동시 로드해 돌릴 수는 있으나 최적화 없이 더 거칠게 자원을 나눔. 이는 이 프로젝트의 원래 출발점(Hailo, YOLOv8 Det/Seg/Pose 3모델 동시추론) 구조를 그대로 되살리는 것.

**제안**: "우리 측 모델 2개 이상 동시실행"을 새 축(M)으로 추가해 Galaxy AI(BLG/Nx)와 별도의 **클린 대조군**으로 배치.

- **왜 클린한가**: Galaxy AI 쪽 응답시간은 블랙박스라 수동 스톱워치로만 측정 가능(19-4의 노이즈 문제). 반면 "우리 모델 A + 우리 모델 B"는 둘 다 우리 코드라 양쪽 다 정밀 내부 타임스탬프로 측정 가능 — 노이즈 없는 기준선(ground truth)이 됨.
- **설계(예)**: YOLOv8-Det + ResNet18, 또는 LLM + ResNet 동시 실행, compute_unit 조합(둘 다 NPU / NPU+GPU 분산 등)별로 스윕.
- **역할 분담**: Track 1(우리 모델끼리, 정밀 계측, M축) = 대조군/보정 기준선. Track 2(우리 모델 vs Galaxy AI, 19장 Nx) = 실사용 시나리오, 노이즈 있음. Track 1의 경합 패턴이 Track 2에서도 비슷하면 "일반적 다중모델 경합 효과", Track 2에서만 유독 심하면 "Galaxy AI/삼성 특유의 효과"로 구분 가능 — RQ7-2(삼성 우대 여부) 결론의 신뢰도를 높여줌.

### 20-3. 리스크

- VLM 온디바이스 배포 경로가 GenieX와 같은 SDK인지, AI Hub의 별도 파이썬/네이티브 배포 경로인지 미확인 — 실기·문서 재확인 필요.
- M축까지 더하면 변인이 더 늘어남(compute_unit×BLG/Nx×M×모델종류) — 12~19장에서 계속 지적된 "시간 예산" 문제가 심해짐. 최소판은 M축을 Track 1(대조군) 하나로만 한정하고 정식 매트릭스엔 넣지 않는 걸 권장.

## 22. 추가 문헌 조사 — 스마트폰 AI 관련 폭넓은 논문 (2026-08-06)

**배경**: 지금까지는 "LLM 추론 NPU 경합"이라는 좁은 주제로만 논문을 찾았는데, 스마트폰 AI 전반으로 넓혀서 재탐색.

### 22-1. 자원경합/공정성 스케줄링 — RQ7-2에 직접 영향

- **"Taming Memory Bandwidth Contention in Mobile LLM..."**(OSDI 2026) — **가장 중요한 발견**: "모바일 OS는 NPU에 대한 관측·제어 수단이 없고, 전력관리 프레임워크가 NPU 트래픽을 아예 배제해서 OS 스케줄러 입장에서 NPU는 '보이지 않는' 존재"라고 명시. **RQ7-2 가설을 정교화해야 함을 시사** — "안드로이드 OS가 삼성 프로세스를 우대한다"는 표현보다는 "우대가 있다면 일반 OS 프로세스 스케줄러가 아니라 QNN/HTP 드라이버 레벨의 Graph Priority(협조적 선점) 메커니즘을 통해서일 것"으로 13-1-A/18-2의 서술을 다듬을 것.
- **V10: Hardware-Assisted NPU Multi-tenancy**(ISCA 2023) — 멀티테넌트 NPU 워크로드용 공정성 지표를 직접 제안 + 오퍼레이터 단위 선점 메커니즘. 20-2(M축)의 "공정성을 어떻게 정량화할까"에 참고할 지표 정의 있음.
- **XSched: Preemptive Scheduling for Diverse XPUs** — GPU/NPU/ASIC 등에 선점형 스케줄링(우선순위/공정성)을 부여하는 프레임워크. "XPU는 원래 이런 유연한 스케줄링 기능이 없다"는 문제의식이 RQ7 전체와 통함.
- **ApproxDet**(콘텐츠·경합 인지형 근사 객체탐지) — 20-1의 CV모델(YOLOv8/ResNet) 경합 실험에 참고할 방법론.

### 22-2. 모바일 VLM — 20-1 계획 보강

- **MobileVLM / MobileVLM V2** — Snapdragon 888 CPU에서 21.5 tok/s 달성한 경량 VLM(1.4B/2.7B). 우리보다 구형 칩 기준치라 비교 기준점으로 유용.
- **MagicVL-2B**(2026-08) — 경량 비전 인코더 기반 최신 모바일 VLM.
- **"Efficient Deployment of Vision-Language Models on Mobile Devices: A Case Study on OnePlus 13R"**(2026) — **우리 프로젝트와 성격이 가장 비슷한 선행연구** — 실제 상용 스마트폰 한 대에 VLM을 배포한 사례 연구. 방법론 비교 대상으로 직접 인용 가치 높음.
- **ARIA**(MobiSys 2025) — 이기종 모바일 프로세서 위 비전 파운데이션 모델 추론 최적화. 20-2 M축과 밀접.
- **CoVSpec**(2026) — 디바이스-엣지 협업 추론(스펙큘레이티브 디코딩)으로 VLM 가속. 온디바이스 단독이 힘들면 참고할 대안 아키텍처.

### 22-3. 배경/서베이

- **"Empowering Edge Intelligence: A Comprehensive Survey on On-Device AI Models"**(arXiv 2503.06027) — 온디바이스 AI 모델 전반 서베이, 보고서 관련연구 절 초안에 활용 가능.
- 배경 통계: 모바일 메모리 대역폭 50~90GB/s vs 데이터센터 GPU 2~3TB/s(30~50배 격차) — BLG 실험에서 "메모리 대역폭 경합"이 왜 유력한 병목인지 설명할 때 인용 가능.
- 프라이버시 맥락(연관도 낮음, 참고용): federated learning 관련 논문들(FLSys 등) — 이 프로젝트는 FL을 안 다루지만 "온디바이스=프라이버시"라는 삼성 마케팅 서사의 더 넓은 학계 맥락으로 인용 가능.

## 23. 논문 핵심 실험 확정안 — 디스패처는 향후 과제로 분리 (2026-08-06 확정)

## 24. llama.cpp를 메인 측정 도구로 확정 + GPU 백엔드 정정(Vulkan→OpenCL) (2026-08-06 확정)

**배경**: "GPU 병목 원인을 정확히 규명하고 실험 환경을 100% 통제하고 있다는 걸 증명하려면, GenieX 대신 llama.cpp를 S26 Ultra에 올려 백엔드(CPU/GPU/NPU)별로 강제 할당 테스트를 해야 한다"는 제안에서 출발.

### 24-1. 결정 — llama.cpp를 Tier1/Tier2 전체의 메인 도구로 승격

10-A-1/16/21장에서 이미 확인해둔 llama.cpp의 강점(`D=` 변수로 CPU/GPU/NPU 백엔드 명시 강제, `llama-bench` 표준 출력이 tok/s·TTFT 자동 산출, 헤드리스 CLI라 Track B 포그라운드 충돌 회피)이 Track B에 국한되지 않고 **Tier1/Tier2 전체의 기본 도구**로 쓸 이유가 된다고 판단해 승격. 화이트박스 백엔드 강제 지정은 그 자체로 Phase 1의 "NPU 실제 점유 검증" 항목을 해결하는 수단이기도 함(`ggml-hex: Hexagon Arch version v81` 같은 로그로 실제 실행 위치가 드러남). GenieX(Developer Preview, 세션 동시로드 미확인)·ExecuTorch(NDK 빌드 난이도 높음)는 보조/백업으로 유지.

### 24-2. 정정 — GPU 백엔드는 Vulkan이 아니라 **OpenCL**

제안에는 "Vulkan 백엔드로 빌드해 GPU 병목을 검증한다"는 내용이 포함돼 있었으나, 확인 결과 이는 부정확함:

- llama.cpp 공식 Snapdragon 문서(`docs/backend/snapdragon/README.md`)는 세 백엔드를 **CPU / Adreno GPU(GPUOpenCL) / Hexagon NPU(HTP0-4)**로 명시 — GPU 경로는 처음부터 OpenCL 기반이고 Vulkan은 공식 문서에 등장하지 않음. Adreno 750/830(Snapdragon 8 Gen3/8 Elite, 즉 S24U/S26U) 지원이 명시적으로 확인됨.
- llama.cpp에 별도로 존재하는 범용 Vulkan 백엔드(`ggml-vulkan`)는 GitHub 공식 이슈/디스커션(#9464 등)에서 **Adreno GPU에 한해 모델 로드 자체가 실패(크래시)**한다는 보고가 다수(Mali GPU는 느리게라도 동작하지만 Adreno는 아예 안 됨). 커뮤니티에서도 "Adreno에는 OpenCL 백엔드가 대안으로 권장된다"고 명시.
- Qualcomm도 이 문제를 인지해 Adreno 전용 OpenCL 백엔드를 별도로 공식 도입(Qualcomm 개발자 블로그 "Introducing the New OpenCL GPU Backend in llama.cpp for Qualcomm Adreno GPUs").

→ **GPU 강제 테스트는 반드시 `GGML_OPENCL`(OpenCL/GPUOpenCL) 빌드로 진행**. Vulkan 빌드는 시도하지 않음(모델 로드 실패로 데이터 자체가 안 나올 위험). `STUDY_DESIGN.md` Phase 0에 이미 반영함.

### 24-3. 종합

이 정정을 빼면 원 제안의 방향(백엔드 강제 지정으로 화이트박스 검증, GenieX 의존 축소)은 기존 계획(10-A-1/16/21장)과 정확히 일치하고 오히려 이를 더 명확히 확정하는 역할을 함.

## 25. 입력 프롬프트를 ShareGPT 데이터셋으로 확장 (2026-08-12 확정)

**배경**: "모델 툴은 llama.cpp로, 입력데이터는 Hugging Face에서 가져와서 쓰자"는 제안에서 출발. 모델 가중치(GGUF)는 이미 Hugging Face에서 받고 있었으나(4장, `LLAMACPP_SETUP_GUIDE.md`), "입력데이터"가 가리키는 건 **프롬프트**였음이 확인됨.

### 25-1. 기존 고정 프롬프트의 출처 재검증

기존 계획(4장)의 프롬프트가 "arXiv 2603.23640 논문의 프롬프트를 그대로 재사용"이라고 되어 있었는데, `RELATED_PAPERS.md`에 "대부분 원문 전체를 정독하지 않고 검색 결과 요약 기반으로 정리함"이라는 경고가 있어 이 인용이 실제 원문 기반인지(과거 세션이 지어낸 건 아닌지) 의심이 제기됨.

→ **원문 대조로 검증 완료(2026-08-12)**: https://arxiv.org/html/2603.23640v2 §3.2("Prompt and Generation Configuration")에 "All platforms receive an identical prompt (UTF-8, 258 tokens as tokenised by the Qwen 2.5 BPE tokenizer)..."라는 문장과 함께 "consciousness를 철학·신경과학·인지과학·AI·윤리 다섯 관점에서 설명하는 에세이" 프롬프트 전문이 그대로 실려 있음을 확인. 기존 인용은 정확했음.

### 25-2. 결정 — 고정 프롬프트는 유지, ShareGPT를 별도 조건으로 추가

- **논문 비교 트랙(기존, 유지)**: 위 258토큰 고정 프롬프트. 이 프롬프트를 바꾸면 arXiv 2603.23640과의 직접 수치 비교가 깨지므로 그대로 둔다.
- **현실 입력 분포 트랙(신규)**: 고정 프롬프트 하나만으로는 실제 사용 시의 입력 길이·내용 다양성을 반영하지 못한다는 문제의식에서, **ShareGPT 데이터셋**(실사용자-ChatGPT/Vicuna 대화 스크랩)에서 프롬프트를 샘플링해 Tier 1/Tier 2 동일 매트릭스에 별도 조건으로 추가 측정한다.
  - **출처**: https://huggingface.co/datasets/anon8231489123/ShareGPT_Vicuna_unfiltered (2026-08-12 페이지 확인 — 약 5.3만 대화, `ShareGPT_V3_unfiltered_cleaned_split.json`/`..._no_imsorry.json` 두 버전, 4.35GB, Apache 2.0)

## 26. 다른 AI 도구의 5개 논리적 비평 검토 + 지도교수 범위 승인 (2026-08-12 확정)

**배경**: 다른 AI 도구(ChatGPT 등)가 `STUDY_DESIGN.md`를 검토하고 5개 논리적 결함을 지적. 전부 검토한 결과 타당한 지적으로 판단해 반영함.

### 26-1. Tier 1의 HTP v69 미지원 문제 (가장 치명적으로 지적됨)

**지적**: 6장에 "llama.cpp 공식 빌드에 HTP v69(S22/Fold4/Flip4) 미포함 → CPU 백엔드로 대체"라고 돼 있었는데, Tier 1의 목적이 "플랫폼(기기·폼팩터) 차이" 비교인데 S24U/S26U는 NPU, S22/Fold4/Flip4는 CPU로 돌리면 이건 기기 차이가 아니라 **NPU vs CPU 백엔드 차이**를 재는 꼴이 됨.

**해결 — 지도교수 승인으로 범위 축소**: 지도교수가 "S24U·S26U 두 기기만으로도 충분하다"고 승인함. 이에 따라 **필수 확정 범위를 Tier 2(S24U vs S26U)로 좁히고, Tier 1의 6기기 전체 비교는 시간이 남으면 진행하는 선택 확장 과제로 격하**했다(`STUDY_DESIGN.md` §3). 이 승인 덕분에 v69 문제 자체가 필수 범위에서는 더 이상 걸림돌이 아니게 됨. 만약 나중에 선택 확장으로 S22/Fold4/Flip4를 실제로 추가한다면, 지적대로 **CPU 트랙(6기기 전체 동일 백엔드)과 NPU 트랙(S24U·S26U만)을 분리**해서 비교해야 하며, 절대 백엔드가 섞인 채로 "기기 차이"라고 결론 내리면 안 된다.

### 26-2. 조건 A/B/C에서 CLI 스케줄링 페널티의 대칭성 착시

**지적**: "모든 인스턴스를 CLI로 실행하니 상대비교가 공정하다"는 가정은, 절전모드(조건 C)·동시실행(조건 B)에서 OS 스케줄러가 포그라운드 GUI와 백그라운드 CLI에 다른 DVFS/코어 배정 정책을 적용할 수 있다는 점을 놓치고 있음 — CLI 페널티 자체가 조건마다 달라질 수 있어 대칭성이 깨질 위험.

**반영**: `STUDY_DESIGN.md` §3에 조건 A/B/C별로 `dumpsys cpuinfo`·`/proc/<PID>/cgroup`으로 P-코어/E-코어 배정을 실측·기록하는 절차를 추가.

### 26-3. B1/B2 간섭 원인의 NPU 내부/외부 DRAM 혼동

**지적**: decode가 memory-bandwidth-bound라고 이미 확인했으면서, B1/B2의 성능 저하를 "NPU 코어/VTCM 경합"으로만 해석할 위험이 있음. 실제로는 두 모델이 요구하는 LPDDR 대역폭 합이 물리적 상한을 넘어 DRAM 버스에서 병목이 생겼을 수 있고, 이 경우 v81 아키텍처 개선으로도 해소 안 됨.

**반영**: `STUDY_DESIGN.md` §5 분석절차에 B3(prefill×decode 겹침)를 NPU 내부(연산집약) vs 외부 DRAM(대역폭집약) 경합을 가르는 통제실험으로 명시.

### 26-4. sysfs devfreq 와일드카드 경로의 실효성 의문

**지적**: 최신 안드로이드/SoC는 보안·파워도메인 개편으로 NPU/CDSP devfreq가 비루팅 권한에 노출 안 되거나 루팅 필요 경로로 옮겨졌을 가능성이 높음.

**반영**: `STUDY_DESIGN.md` §5-A A-3을 "Snapdragon Profiler를 메인, sysfs는 Phase 1에서 `find`로 확인 후 안 되면 즉시 포기하는 2차 보조 수단"으로 격하.

### 26-5. ShareGPT 샘플링 시 prefill/decode 분리 통제 누락

**지적**: ShareGPT 트랙은 프롬프트 길이가 버킷마다 다른데, prefill은 입력 길이에 비선형 증가·decode는 출력 토큰당 선형이라, aggregate tok/s만 보면 착시가 생김.

**반영**: `STUDY_DESIGN.md` §4-A에 "버킷별로 TTFT(prefill)와 decode 토큰당 시간을 분리 파싱해서 비교" 원칙 추가 — CSV 스키마(§4 Phase 0)에 이미 있는 `ttft_ms`/`prefill_time_ms`/`decode_time_ms` 컬럼을 활용.

### 26-6. 출처 및 검증 상태

이 절의 5개 지적은 다른 AI 도구가 생성한 비평이며, 이 프로젝트에서 각각의 논리적 타당성을 직접 검토해 전부 타당하다고 판단하고 반영했다(사실 인용이 아니라 방법론적 추론이라 외부 문헌 대조 검증 대상은 아님). 지도교수의 Tier 1 범위 축소 승인은 2026-08-12 대화 기준.

## 27. Tier 2 조건 B4 추가 — GenieX 병행 FG/BG 조합 검증 (2026-08-12 확정)

**배경**: "실험 이후에는 GenieX와 같이 써서 포그라운드 vs 백그라운드 / 포그라운드 vs 포그라운드 / 백그라운드 vs 백그라운드도 실험해서 분석하자"는 제안. §3의 "핵심 설계 원칙 — OS 백그라운드 스로틀링 통제" 절이 이미 "CLI 페널티가 조건마다 다를 수 있다"는 우려를 `dumpsys cpuinfo` 실측으로 검증하겠다고 해뒀는데, 이 제안은 그 우려를 **가정이 아니라 실제 앱 생명주기(foreground/background)로 직접 실험**해보자는 확장.
