## 1. 연구 주제·목표

삼성 갤럭시 스마트폰(스냅드래곤 기반)에서 온디바이스 AI를 실행할 때의 **NPU 추론 성능**을 실측하는 연구다. 세 가지를 확인한다.

1. NPU 컴퓨트 유닛과 기기·폼팩터에 따라 추론 성능이 얼마나 유지·저하되는지 (CPU는 베이스라인, **GPU는 측정 제외**).
2. **여러 온디바이스 AI 모델이 같은 NPU(Hexagon HTP)를 동시에 점유할 때** 처리량·지연·전력이 어떻게 저하·간섭되는지, 그리고 그 간섭 패턴이 **S24U(HTP v75)와 S26U(HTP v81)의 아키텍처 세대차로 어떻게 설명되는지**.
3. 삼성이 광고하는 세대 간 성능 개선("NPU 향상, 멀티태스킹 문제없음")이 단독뿐 아니라 **동시실행·절전 제약에서도** 유지되는지.

실험은 두 단계다. **Tier 1**은 보유 기기 5대(S22, Z Fold4, Z Flip4, S24U, S26U) + 데스크탑의 전체 플랫폼 단독 비교, **Tier 2**는 핵심 기여로 S24U·S26U만 놓고 단독(A) / 멀티모델 동시실행(B) / 절전(C) 조건에서 세대 격차가 유지되는지 비교한다.

> **2026-08-11 방향 재설계**: 원래 2번은 "삼성 자사 Galaxy AI와의 경합 및 공정성(RQ7)"이었으나, Galaxy AI가 블랙박스 앱이라 추론 성능을 직접 측정할 수 없어(카메라 프레임 분석 우회에 의존) 폐기했다. 경합 상대를 우리가 통제 가능한 우리 측 멀티모델로 바꿔 **전 워크로드를 화이트박스(llama.cpp)로 직접 계측**하고, 세대별 NPU 아키텍처 조사로 원인을 설명하는 방향으로 전환했다.

## 2. 방법

측정 도구는 처음엔 퀄컴 GenieX SDK를 검토했으나 개발자 프리뷰 단계라 안정성이 불확실하고 Android 앱 빌드 진입장벽이 커서, **llama.cpp를 메인 측정 도구로 전환**했다. llama.cpp는 CLI `--device` 옵션으로 CPU/NPU를 명시적으로 강제 지정하는 화이트박스 도구라 "정말 지정한 하드웨어를 쓰는가"를 직접 검증할 수 있다. NPU는 Hexagon 백엔드를 쓴다(GPU/OpenCL 백엔드는 측정 제외).

파이프라인은 Docker 기반 Snapdragon 전용 툴체인으로 안드로이드용 바이너리를 빌드→adb로 폰에 설치→adb shell로 원격 실행하는 구조다. 하드웨어 실측치(NPU 활용률·클럭)는 Snapdragon Profiler로 교차검증한다. 프로토콜은 선행연구(arXiv 2603.23640)를 그대로 채택 — 10분 열안정화, 워밍업 폐기, 20회 반복, 3세트.

**멀티모델 동시실행(Tier 2 조건 B)** 구성: (B1) 이종 LLM+CNN, (B2) 크기 다른 동종(대+소 LLM), (B3) prefill×decode 겹침. 동시 인스턴스 수 N을 포화까지 스윕한다. **아키텍처 조사**는 HTP v75 vs v81 스펙(HMX/HVX, VTCM, 대역폭, 클럭, V81 Concurrent Resource Sharing)을 문헌으로 조사하고 마이크로벤치(대역폭 roofline·VTCM 포화점·컨텍스트 스위칭 비용)로 뒷받침해, 간섭 결과의 원인을 설명한다.

## 3. 발생한 문제와 해결

이 연구는 "문서상 가능해 보이는 것"과 "실기에서 실제로 되는 것"이 계속 어긋나는 경험의 연속이었다.

- **설계 단계**: (구 설계의) 배경부하 Galaxy AI 기능 후보가 세 번 반박됨 — 유튜브는 GPU 연산을 안 뺏고(동영상 디코딩은 전용 HW), 오브젝트 지우개는 클라우드 전환 정황, 노트 번역은 항상 언어팩 요구. 통역만 실기(비행기모드) 검증을 통과했으나, 결국 **블랙박스 측정 한계로 Galaxy AI 경쟁실험 자체를 폐기**하고 화이트박스 멀티모델 동시실행으로 전환.
- **설치 단계**: llama.cpp 빌드 시 웹 UI 임베드 컴파일 실패·테스트 헤더 오류·통합 바이너리 실패가 연달아 발생 → 소스 분석으로 원인 CMake 옵션(`LLAMA_BUILD_SERVER/TESTS/APP=OFF`)을 찾아 해결. Docker/adb PATH 미인식, 파일 전송 실행권한 누락, 목적지 폴더 미생성(`mkdir` 누락) 등 환경 이슈도 반복.
- **결과 해석 단계**: 컴퓨트 유닛 활용률이 예상보다 크게 낮게(1~2%) 측정 → 화이트박스로도 재현돼 도구 문제 아님을 확인. prefill(연산집약) vs decode(대역폭집약) 분리 측정에서 ~44배 처리량차 → **LLM decode가 메모리 대역폭 병목**이라는 추론 구조 인사이트 도출. 이는 **NPU 세대별 대역폭 차이 = 성능차 원인**이라는 아키텍처 분석의 직접 근거로 승격됨.

## 4. 현재 상황

**연구 설계**: 2026-08-11 재설계로 Tier 1/Tier 2 구조, 측정 도구(llama.cpp), 멀티모델 동시실행 워크로드(B1/B2/B3), NPU 아키텍처 조사(문헌+마이크로벤치), GPU 측정 제외까지 확정.

**실기 진행**: S26U에서 개발환경(Snapdragon Profiler 연결)을 먼저 구축, 이후 S24U에서 llama.cpp를 빌드→설치→실행까지 성공. 핵심 검증 항목인 **"NPU를 실제로 쓰는가"를 실행 트레이스로 확인 완료** — 17/17 레이어 전부 Hexagon HTP0에 배정·실행, HTP 큐 push/pop 타이밍(배치당 ~14ms)까지 관측.

**다음 단계**:
1. **llama.cpp 다중 인스턴스가 같은 HTP에서 실제 동시 스케줄되는지 검증**(verbose 로그 큐 인터리빙) — 조건 B의 전제, 신규 최우선.
2. 나머지 3대(S22, Z Fold4, Z Flip4) 개발자모드·USB디버깅 활성화 및 환경 구축.
3. HTP v75 vs v81 문헌 스펙 조사 착수(병행 가능).
4. Tier 1 데이터 수집 → 멀티모델 동시실행(Tier 2) 측정 → 아키텍처 원인분석.
